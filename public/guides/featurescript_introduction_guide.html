    Introduction to FeatureScript for Onshape

    This guide takes you from opening a Feature Studio to writing a real custom feature: a parameterized, 3D-printable holder for the REV slim battery that you can drop into any Part Studio, change with a dialog, and print. Along the way you will learn the language itself, the sketching and modeling operations, and the query system that selects the geometry you want to change.

    Who this is for. You can build parts in an Onshape Part Studio: sketches, extrudes, fillets, patterns. You have some programming background and you can think computationally, so you can adapt to a new language. That is all this guide assumes. You do not need to know FeatureScript, or any other CAD scripting language. Every new idea is introduced where you first need it, and every code example is small enough to read in one sitting.

    What you will finish with

    By the end you will have a working custom feature, the REV slim battery holder, that builds a protective slide-in sleeve for the REV Robotics 12 V slim battery (REV-31-1302). It is parameterized: battery length, width, and height, slide clearance, wall and base thickness, wall height, lip size, and the mounting-hole pattern are all dialog fields with sensible defaults. Change a number, and the holder rebuilds.

    A working feature

    One FeatureScript file that builds the holder from eleven steps: sketches, extrudes, and booleans, with the battery sliding in through an open end and held down by lips.

    The language

    Types, units, functions, control flow, and errors, with the rules that actually bite: sketch points need length units, and there is no Length type.

    The standard library

    The working set: sketching, extrude and boolean, revolve, fillet, chamfer, loft, thicken, and the queries that select bodies, faces, and sketch regions.

    The holder is not trying to be the most clever battery mount ever designed. It is trying to be the smallest real feature that exercises every decision a real feature has to make: parameters with bounds, sketches on offset planes, extrudes that become tools, booleans that merge and cut, and entity identity tracked across all of it. Once those decisions are in place, writing your own feature is mostly a matter of writing more steps in the same shape.

    What FeatureScript actually is

    FeatureScript is a programming language that lives inside Onshape. You write code in a Feature Studio, and that code defines a custom feature: a new entry in the feature list of a Part Studio, with its own dialog, that builds geometry when it regenerates.

    The three things a feature does

    Every feature, from the simplest block to the battery holder, does three things in order:

    1. Read parameters. The feature dialog gives you values: lengths, angles, counts, selections. The feature reads them from a map called definition.
    2. Build sketches. Two-dimensional profiles on planes, made of lines, arcs, circles, and rectangles, then solved.
    3. Run operations. Extrude a sketch region into a solid, merge two solids, cut a hole, fillet an edge. Each operation changes the Part Studio.

    That is the whole mental model. Everything else in this guide is detail on one of those three steps: how parameters are declared and bounded, how sketches are built and what can go wrong with their points, and how operations and queries select the geometry they act on.

    Features, operations, and the Context

    WordWhat it means here
    Feature StudioA tab in an Onshape document where you write FeatureScript. It holds one or more features. It is not a Part Studio: nothing in it is a part until a feature runs.
    FeatureA function you define with defineFeature. It takes a Context, an Id, and a definition map, and it appears in the Part Studio feature list with a dialog.
    Operation (op)A standard-library function such as opExtrude or opBoolean that changes the Context. Operations are the verbs: they make, merge, cut, and reshape geometry.
    ContextThe Part Studio's modeling data: bodies, entities, variables, and feature error states. Every Part Studio uses a single Context, and every feature, operation, and evaluation function needs one.
    QueryA description of which entities you mean, such as "the body created by the base extrude" or "all faces of this sketch region". Queries are how operations find their inputs.
    SketchA two-dimensional drawing on a plane, built from sketch entities and then solved with skSolve. Sketches are the raw material for extrudes and revolves.

    How a feature runs

    When a Part Studio regenerates, Onshape runs each feature in order, top to bottom. A feature receives the Context as it stands after the features above it, runs its operations, and hands the changed Context to the next feature. If a feature throws an exception, it fails, the error appears in the notices flyout, and the features below it do not run. That is why the errors chapter matters: a feature that fails loudly with a clear message is much easier to fix than one that fails silently.

    Each Context also records the standard-library version it was created at, so a feature held back to an older version emulates old behaviour. That is the mechanism behind version pins like 3112.0: the version in your import is the behaviour your feature was written against.

    Five words you will meet

    WordWhat it means here
    DefinitionThe map of dialog values your feature receives, called definition. definition.batteryLength is the length the user typed in the dialog.
    PreconditionA block after the feature's argument list that validates the parameters. It also defines the dialog: each parameter line becomes a field.
    IdA hierarchical name for a feature or operation, built with +, such as id + "base". Operations and queries use ids to refer to each other.
    ValueWithUnitsA number with dimensions, such as 113.5 * millimeter. Lengths, angles, and every other physical quantity are values with units. There is no separate Length type.
    RegenerateOnshape re-running the feature list to rebuild the part. Every edit to a dialog value, and every edit to the code, regenerates.

    Roadmap and versions used in this guide

    The guide is written against FeatureScript 3112 and the standard library common.fs 3112.0. This chapter says exactly what that pin means, what it does not mean, and the order the rest of the guide follows.

    The version pin, honestly

    Every Feature Studio begins with a version statement, and every standard-library import names a version:

    FEATURESCRIPT
    FeatureScript 3112;
import(path : "onshape/std/common.fs", version : "3112.0");

    The battery holder file uses exactly these two lines, and this guide follows it. But there is a caveat you should know about, because it affects how much to trust the pin: the FsDoc pages this guide was checked against do not stamp themselves with a version number. Nothing in the pages as served says "this documents FeatureScript 3112", and no "changed in 3112" notes were found. The library examples in the docs still show old versions, such as 300.0 in an import example, and the tutorials use FeatureScript 1890;.

    So the signatures in this guide are the current FsDoc as read on 7 November 2026, and the 3112 pin is the file header and import, not something independently confirmed from a version stamp in the docs. In practice the pin is confirmed the other way: paste the code into a Feature Studio, and Onshape runs it against 3112. If a signature had changed, the Feature Studio would say so. The test chapter at the end of the running example is that check.

    Why common.fs and not geometry.fs. The standard library comes in two imports. onshape/std/common.fs is the common subset, without the full geometry features; onshape/std/geometry.fs is the full library. The holder uses common.fs, and everything in this guide's working set is in it. If you later need a function that is only in geometry.fs, change the import path and the version stays the same.

    Set up a Feature Studio

    There is no installer and no build step. A Feature Studio is a tab in an Onshape document, and the feature runs when the Part Studio regenerates. Do this once, and every example in this guide has somewhere to live.

    Create the Feature Studio

    1. Open the document where the feature should live. Any document works; the running example uses the document that holds the robot parts.
    2. Create a Feature Studio. Right-click a tab and choose Create Feature Studio, or click the + at the bottom left and choose Feature Studio.
    3. Paste the code. Paste the whole file into the Feature Studio. The version header goes first, then the import, then the code.
    4. Check for errors. Look at the notices flyout. A Feature Studio with no errors shows the feature name in the toolbar; an error names the exact operation that failed.

    Use the feature in a Part Studio

    1. Open a Part Studio in the same document.
    2. Open the custom-feature dropdown in the feature toolbar. Your feature appears there under the name from its annotation, for example "REV Slim Battery Holder".
    3. Click it. The feature is added to the feature list, its dialog opens, and the part builds with the default parameters.
    4. Change a parameter and watch it rebuild. Type a new battery length, press Enter, and the holder regenerates. That loop — change a number, watch the part — is how you test everything in this guide.

    What the import line does

    The import line makes the standard library available to your code. The docs show the import with an empty version, and Onshape inserts the current version when you create it that way. The holder pins the version explicitly instead:

    FEATURESCRIPT
    import(path : "onshape/std/common.fs", version : "3112.0");

    Pinning the version means the feature keeps the behaviour it was written against, even if a later standard-library version changes a signature. Each Context records the version it was created at, so a feature held back to an older version emulates the old behaviour. For your own features, pin the version you developed against, and bump it deliberately when you want the new behaviour.

    There is also a namespaced form, used when you want the import under your own namespace instead of the global one:

    FEATURESCRIPT
    myNamespace::import(path : 'onshape/std/math.fs', version : '255.0');

    You will not need it for this guide. The plain import is the normal form.

    Reading error messages. When a feature fails, the notices flyout names the operation and the reason, for example a precondition failure or a query that resolved to nothing. The debugging chapter collects the errors you will actually meet and what each one means. For now, remember only this: the error names the exact operation, and the step numbers in the holder's comments map one to one to the build order, so the failing step is easy to find.

    Types and values

    FeatureScript is dynamically typed: every value has exactly one standard type, and type errors are found while the code runs, not before. There are nine standard types, and a value can also carry one type tag, which is how enums and custom types work.

    The nine standard types

    TypeWhat it holds
    booleantrue or false only. There is no implicit conversion: write if (x != 0), not if (x).
    numberAn IEEE 64-bit double. It includes -0, -inf, and +inf, but not NaN: an operation that would return NaN throws immediately, for example the square root of a negative number.
    stringText. The ~ operator concatenates.
    arrayAn ordered, heterogeneous, zero-based collection. An out-of-range read throws, and arrays do not grow on write.
    mapA heterogeneous collection keyed by any value. String keys can be used unquoted when they are valid identifiers.
    boxA mutable cell: new box(value), read and changed with b[]. With builtin, the only way to share mutable state.
    functionA function value, including a lambda.
    builtinAn opaque value created by the standard library. A Context is one.
    undefinedThe value of a variable that has not been set, and of a function that falls off the end without returning.

    Variables: var, const, and type constraints

    FEATURESCRIPT
    var count = 0;
count = count + 1;          // var is reassignable

const wall = 3 * millimeter;
// wall = 4 * millimeter;   // error: a const cannot be reassigned

var y is number = 1;        // a type constraint, checked on every assignment
var z is Vector = vector(0, 0);

    A variable declared with a type must satisfy that type on every assignment, and it must be initialized immediately. The constraint is written after the name with is, the same is that tests a type elsewhere in the language.

    Arrays

    FEATURESCRIPT
    var numbers = [1, 2, 3];
var first = numbers[0];     // zero-based indexing
var mixed = [1, "two", 3 * millimeter];  // arrays are heterogeneous
var missing = numbers[9];   // throws: out-of-range read
var safe = numbers?[9];     // safe navigation: undefined instead of throwing

    Arrays do not grow when you write past the end. If you need a longer array, build a new one. The safe-navigation form ?[...] reads as undefined instead of throwing, which is useful when a value may legitimately be absent.

    Maps

    FEATURESCRIPT
    var dims = { "length" : 113.5 * millimeter, "width" : 90.5 * millimeter };
var len = dims.length;      // dot access for string keys
var w = dims["width"];      // bracket access works too
var key = "length";
var same = dims[key];       // brackets use the variable's value as the key
var absent = dims.height;   // a missing key reads as undefined
dims.height = undefined;    // assigning undefined removes the key

    Maps are heterogeneous, and they are ordered deterministically, so iterating a map always visits the keys in the same order. If you know Python, a map is closest to a dict, except that a missing key reads as undefined instead of raising, and assigning undefined deletes the key.

    Parentheses do appear with maps, but in a different place: in a map literal, a parenthesized key uses a variable's value as the key. With var b = 2;, the literal { (b) : "two" } makes the key 2, not the string "b"; without the parentheses, b would be read as the string key "b". That is a literal-key rule, not an access rule: to read by a variable key you use brackets, dims[key]. Do not write dims.(key) — it does not parse.

    Maps are also how the standard library passes named arguments: almost every operation takes a map of fields, such as { "entities" : ..., "direction" : ... }. You will write maps constantly, and most of them are operation arguments.

    Boxes: the one mutable container

    Every value except a box or a builtin behaves as if it were deep-copied on assignment, on argument passing, and on return. That means a function cannot change its caller's array or map by writing into it. If you genuinely need shared mutable state, use a box:

    FEATURESCRIPT
    var counter = new box(0);
counter[] = counter[] + 1;  // read and write through []

    You will rarely need a box in a feature. The holder uses none. But knowing the rule explains a common surprise: changing a map inside a helper function does not change the caller's map, because the helper received a copy.

    Language coreTypes and values

    Numbers with units: ValueWithUnits

    In FeatureScript, a physical quantity is a number with dimensions. 113.5 * millimeter is not a number with a comment attached; it is a value of the type ValueWithUnits, and the units are part of the value. You multiply a plain number by a unit constant to make one.

    Making values with units

    FEATURESCRIPT
    var length = 113.5 * millimeter;
var angle = 90 * degree;
var area = (20 * foot) * (30 * foot);   // an area, not a length
var ratio = (64 * foot) / (9 * inch);   // the units cancel: a plain number
var half = length / 2;                  // still a length

    Each unit is a constant equal to one of that unit: millimeter is one millimeter, inch is one inch. Multiplying a number by it gives a value with those units, and arithmetic keeps track of the dimensions for you.

    Unit arithmetic and its rules

    FEATURESCRIPT
    var a = 1 * meter == 1000 * millimeter;   // true: units convert
var b = 3 * meter + 1 * inch;             // fine: same dimensions add
// var c = (3 * meter) + (3 * degree);    // throws: different dimensions
var d = sqrt(4 * meter^2);                // 2 * meter
// var e = sqrt(4 * meter);               // throws: no square root of a length
var n = definition.myLength / inch;       // dividing by a unit gives a number

    The rules are the ones you would expect from dimensional analysis: values with the same dimensions add and subtract, across unit systems; values with different dimensions do not; multiplication multiplies the units, and a product whose units cancel completely is a plain number. Dividing a length by a unit gives a number, which is the idiom the holder uses to turn a length into a plain number before building a sketch point.

    Internally a ValueWithUnits is a map tagged ValueWithUnits, with lengths stored in meters. You do not need to know that to use one, but it explains why two lengths in different units compare equal: they are the same quantity. For equality, prefer tolerantEquals, which compares up to a tolerance instead of exactly.

    There is no Length type. This is the single most common wrong assumption in FeatureScript. Lengths are typed ValueWithUnits throughout the library: opExtrude's endDepth is a ValueWithUnits, and a parameter declared is Length is an error. isLength is only a predicate, a test you apply to a value. The holder's helper functions declare their length parameters is ValueWithUnits, which is the correct form.

    Vectors, planes, and lines

    Geometry in FeatureScript is built from a small set of types: vectors for points and directions, planes for sketch surfaces, lines for axes, and coordinate systems and transforms for moving between frames. Learn these four, and every operation signature reads naturally.

    Vector

    A Vector is a non-empty array of numbers or lengths. You build one with vector, and the arithmetic operators are overloaded for it:

    FEATURESCRIPT
    var p2 = vector(0.5, 1) * inch;      // a 2D length vector
var p3 = vector(0, 0, 0) * millimeter; // a 3D length vector
var dir = vector(0, 0, 1);            // a unitless direction vector
var fromArray = vector([1, 2, 3]);
var sum = p3 + vector(1, 0, 0) * millimeter;
var n = norm(dir);                    // length of a vector
var d = dot(dir, vector(0, 1, 0));    // dot product
var c = cross(dir, vector(0, 1, 0));  // cross product
var zero3 = zeroVector(3);            // vector(0, 0, 0)

    The distinction that matters most is between a length vector and a direction vector. A length vector has length units on every component, such as vector(0.5, 1) * inch; a direction vector is unitless and normalized, such as vector(0, 0, 1). Sketch points must be length vectors, and directions must be unitless. Mixing them up is the most common geometry error in this guide, and the sketch-points chapter is devoted to it.

    Related predicates: isLengthVector (all members have length units), isUnitlessVector (all members are plain numbers), is2dPoint (a single 2D length vector), is2dPointVector (an array of 2D length vectors), is2dDirection (a unitless normalized 2D vector), is3dLengthVector, is3dDirection, and isUvVector (a single 2D unitless vector). Also angleBetween(v1, v2), which returns an angle as a ValueWithUnits, and squaredNorm.

    Plane

    A Plane is a map with an origin (a 3D point in world space), a normal (a 3D unit vector), and an x axis (a 3D unit vector perpendicular to the normal):

    FEATURESCRIPT
    var xy = plane(vector(0, 0, 0) * millimeter, vector(0, 0, 1));
var offset = plane(vector(0, 0, 1) * (3 * millimeter), vector(0, 0, 1));
var withX = plane(vector(0, 0, 0) * millimeter, vector(0, 0, 1), vector(1, 0, 0));

    The two-argument form chooses the x-axis arbitrarily, perpendicular to the normal; the three-argument form lets you fix it. The origin is any 3D point in world space, so an offset plane like the second line is an ordinary plane three millimeters above the XY plane. That is how the holder sketches its cavity, lips, and open end at different heights.

    Constants: XY_PLANE, YZ_PLANE, XZ_PLANE. Helpers: planeToWorld, worldToPlane (a 2D result), worldToPlane3D, yAxis(plane), and flip(plane). You can also build a plane from a coordinate system with plane(cSys).

    Line

    A Line is a map with an origin (a 3D point with length units) and a direction (a unitless normalized 3D vector). The line constructor normalizes the direction for you:

    FEATURESCRIPT
    var axis = line(vector(0, 0, 0) * inch, vector(0, 0, 1));

    Constants: X_AXIS, Y_AXIS, Z_AXIS. Lines are used as revolve axes and as the axes for rotations.

    CoordSystem and Transform

    A CoordSystem is a map with an origin (a Vector), an xAxis (a 3D unit vector), and a zAxis (a 3D unit vector perpendicular to the x-axis); the y-axis is the cross product. Build one with coordSystem(origin, xAxis, zAxis) or coordSystem(plane), and convert with toWorld and fromWorld. Constants: WORLD_ORIGIN (which is vector(0, 0, 0) * meter), X_DIRECTION, Y_DIRECTION, Z_DIRECTION (unitless).

    A Transform is a map with a linear part (a Matrix) and a translation (a Vector), representing a change of position and orientation, and also scaling and shearing. Build one with transform(linear, translation) or transform(translation), and use identityTransform(), inverse(t), rotationAround(line, angle), scaleUniformly(scale[, point]), and scaleNonuniformly(...). The * operator composes transforms and applies them. Matrices have their own helpers: matrix(array), identityMatrix(n), zeroMatrix(rows, cols), diagonalMatrix(values), transpose, inverse, determinant, and norm, with MatrixWithUnits as the units-carrying analogue.

    Other geometry types

    You will meet these less often, but they exist in the same family: Path (a series of connected edges forming a continuous path, built with constructPath and reversed with reverse), Box3d (an axis-aligned bounding box, returned by evBox3d), BSplineCurve and BSplineSurface (splines from control points, weights, and knots), and the surface primitives Cone, Cylinder, Torus, and Sphere, each defined by a CoordSystem plus a radius or half-angle.

    Functions, predicates, and overloading

    Functions are values. You define them with function, assign them to variables, pass them as arguments, and overload them by argument count and type. Predicates are a special kind of function that always returns a boolean and is used wherever FeatureScript needs a test: preconditions and typechecks.

    Defining a function

    FEATURESCRIPT
    function fourthPower(x) { return x * x * x * x; }

function fourthPowerChecked(x) returns number { return x * x * x * x; }
// a mismatched return type raises

var f = function(x) { return x + 1; };       // a lambda assigned to a variable
var g = x => x + 1;                          // arrow form
var h = (v is ValueWithUnits) returns ValueWithUnits => v * 2;

function pt(x is ValueWithUnits, y is ValueWithUnits)
{
    return vector(x / millimeter, y / millimeter) * millimeter;
}

    Parameters may carry is <Type> constraints, and arguments are checked the same way the is operator checks a value. A function that falls off the end, or executes a bare return;, returns undefined. The pt function at the end is the holder's sketch-point helper; it takes two lengths and returns a 2D length vector, and the sketch-points chapter explains why it has to exist. A lambda can carry a returns constraint too, as the h example shows.

    There is also an arrow call syntax: x->f(y, z) is equivalent to f(x, y, z). It reads well when the first argument is the thing being acted on, such as a query or a vector.

    Predicates

    A predicate always returns a boolean. It has two restrictions: no assignments and no side-effect statements inside, and no variable declarations except the loop variable in a for (var ... in ...). It succeeds if and only if every expression statement it executes evaluates to true; it fails immediately, returning false, on a false expression statement, and it raises if an expression statement is not true or false.

    FEATURESCRIPT
    export predicate isLumber(value)
{
    value is map;
    value.size is LumberSize;
    isLength(value.length);
}

    That example is a typecheck predicate for a custom type, which the type-tags chapter works through. Predicates are also what preconditions are made of: a precondition is evaluated like a predicate, and if an expression statement fails, an exception is raised and the call is aborted.

    Overloading

    Multiple top-level subroutines may share a name with different argument counts or type constraints. Resolution finds the most specific satisfying overload, and raises if there is none, or if there is no single most-specific one:

    FEATURESCRIPT
    // defineFeature has two overloads in the standard library:
defineFeature(feature is function) returns function
defineFeature(feature is function, defaults is map) returns function

    Operator overloads are allowed for +, -, *, /, %, ^, <, and unary -. At least one argument must have a custom-type or enum constraint. Overloading + also applies to +=, and overloading < also applies to >, <=, and >=. This is how Vector arithmetic works: + and * on vectors are overloads defined by the library.

    Control flow and operators

    FeatureScript's control flow is small: if, while, two forms of for, a ternary, and try/catch. There is no switch statement in the syntax page as read. The operators hold the surprises: ^ is exponentiation, ~ is string concatenation, and % takes the sign of its second operand.

    Conditionals and loops

    FEATURESCRIPT
    if (count > 0) { println("positive"); } else { println("not positive"); }

var i = 0;
while (i < 3) { i = i + 1; }

for (var j = 0; j < 3; j = j + 1) { println(j); }  // C-style for

for (var item in [1, 2, 3]) { println(item); }      // for-in over an array
for (var k, v in myMap) { println(k ~ ": " ~ toString(v)); }  // key and value

var label = (count > 0) ? "positive" : "zero or negative";  // ternary

    Conditions must be boolean. That is the rule behind the earlier warning: if (x) with a number is an error, and you write if (x != 0) instead.

    In a C-style for, the increment must be a function call or an assignment. break and continue exist; continue in a for still executes the increment. In a for-in, one variable binds to the item for an array, or to a { key: ..., value: ... } map for a map; two variables bind to the key or index and the value. The var may be omitted to reuse a surrounding variable.

    OperatorMeaning
    - (unary), !Numeric negation, boolean negation.
    + - * / % ^Arithmetic. ^ is exponentiation, and % takes the sign of the second operand.
    ~String concatenation.
    < > <= >= == !=Comparisons. Enums of the same type compare by definition order.
    && ||Logical and/or, short-circuiting.

    try and catch

    Exceptions are covered in full in the errors chapter. The short version: try exists in two forms, an expression form and a statement form.

    FEATURESCRIPT
    var maybe = try (0 / 0);   // expression form: undefined if an exception is raised

try { f(x); }               // statement form: execution continues after the block
try { f(x); } catch { fail(); }
try { f(x); } catch (e) { analyze(e); }

    A try block aborts on the first exception. Without a catch, execution continues after the block; with one, the catch block runs. Features, and the evaluation of feature parameters, run inside a try, and an uncaught exception terminates the program.

    Type tags, enums, and custom types

    Every value has one standard type, and it can also carry one type tag. A type tag is how the language represents enums, such as BoundingType.BLIND, and custom types, such as a Vector or a Plane. The is operator tests a tag, and as adds or removes one.

    is and as

    FEATURESCRIPT
    var v = vector(0, 0, 1);
var isVec = v is Vector;            // true: tests a type tag or standard type
var asText = "A" as Example;        // succeeds if "A" is a member of Example
// var bad = "Z" as Example;        // raises: "Z" is not a member

    x is Vector tests a type tag or a standard type and returns a boolean. v as TypeId adds or removes a type tag. For an enum, the value must be a string member of the enum. Values with different type tags are not equal, and predefined operators on standard types produce a new value without a type tag unless overloaded.

    Enums

    Enums are declared at the top level. An enum value is a string with the enum's type tag:

    FEATURESCRIPT
    export enum LumberSize { TWO_BY_FOUR, TWO_BY_SIX, TWO_BY_EIGHT }

var size = LumberSize.TWO_BY_FOUR;   // the string "TWO_BY_FOUR", tagged LumberSize

    Enums of the same type can be compared with < and the other comparisons, by definition order. Comparing enums of different types throws. This is the mechanism behind every enum in the operations chapters: BoundingType.BLIND is the string "BLIND" tagged BoundingType, and passing a plain string where a BoundingType is expected does not satisfy the type.

    Custom types

    A custom type is a type tag backed by a typecheck predicate:

    FEATURESCRIPT
    export type Lumber typecheck isLumber;
export predicate isLumber(value)
{
    value is map;
    value.size is LumberSize;
    isLength(value.length);
}

    The constructor convention is a lower-case function with the type's name, returning a map with the type tag applied:

    FEATURESCRIPT
    function lumber(size is LumberSize, length is ValueWithUnits)
{
    return { "size" : size, "length" : length } as Lumber;
}

    One honest note from the docs: the typecheck predicate "currently only serves as documentation for the type". Declaring the typecheck does not make the language enforce it at runtime; it documents what a value of the type must look like. The core library types you use every day, such as Vector, Plane, and ValueWithUnits, are custom types in exactly this sense, and their predicates, such as is2dPoint, are where the real checking happens.

    Errors, preconditions, and reporting

    FeatureScript raises exceptions for invalid numeric operations, failing preconditions, a map lookup on undefined, and failing operations, evaluations, or features. How you handle them decides whether a user sees a clear message or a cryptic failure.

    Exceptions and try

    FEATURESCRIPT
    try (0 / 0)                       // expression form: yields undefined
                                  // if an exception is raised
try { f(x); }
try { f(x); } catch { fail(); }
try { f(x); } catch (e) { analyze(e); }

throw;                            // rethrow the current exception
throw "an error has occurred";    // a string error
throw { message : ErrorStringEnum.TOO_MANY_ENTITIES_SELECTED };  // a library error
throw e;                          // rethrow a caught exception

    Language errors are usually strings; library errors are usually maps with a message field of type ErrorStringEnum. Any raised exception is reported in the notices flyout, whether or not it is caught. try silent, in statement or expression form, suppresses that reporting, and should be used cautiously: a silenced error is an error nobody can see.

    Preconditions

    A precondition is evaluated like a predicate: if an expression statement fails, an exception is raised and the call is aborted. That is the mechanism that turns a bad dialog value into a failed feature instead of a wrong part. The define-feature chapter works through preconditions in full; the short version is that a precondition is both a validation and, for a feature, the definition of its dialog.

    defineFeature, annotation, and precondition

    A feature is a function wrapped by defineFeature, with an annotation giving its display name and a precondition block that validates its parameters and defines its dialog. This is the skeleton every feature in this guide hangs from, including the battery holder.

    The shape of a feature

    FEATURESCRIPT
    annotation { "Feature Type Name" : "My Feature" }
export const myFeature = defineFeature(function(context is Context, id is Id, definition is map)
    precondition
    {
        annotation { "Name" : "Depth" }
        isLength(definition.depth, { (millimeter) : [1, 10, 100] } as LengthBoundSpec);
    }
    {
        // build geometry here
    }, {});

    defineFeature has two overloads: defineFeature(feature is function) returns function, and defineFeature(feature is function, defaults is map) returns function. The defaults map supplies FeatureScript-call defaults only, not UI defaults: it affects calling the feature from code, not the dialog. To change a user-visible default, use a "Default" annotation for booleans, enums, and strings, and the valueBounds module for a length, angle, or number. The empty map {} at the end of the example is that defaults map, passed empty.

    The annotation above the feature gives the name shown in the custom-feature dropdown and the feature list. Without it, the feature has no display name. The export makes the feature visible outside the Feature Studio, which is what lets a Part Studio use it.

    The precondition block

    The precondition sits between the argument list and the body, and is usually a block. It can also be a single statement:

    FEATURESCRIPT
    function sqrt(n is number) returns number
    precondition n >= 0;
    { ... }

function makeArray(n is number) returns array
    precondition { isInteger(n); n > 0; }
    { ... }

    A precondition is evaluated like a predicate: if an expression statement fails, an exception is raised and the call is aborted. In a feature, the precondition does a second job: it defines the feature dialog. Each definition.<param> is <Type>; line, with an annotation { "Name" : ... } above it, becomes a dialog field, and predicates such as isLength(definition.depth, LENGTH_BOUNDS); validate it. That is why the holder's precondition is twelve annotated isLength lines: those twelve lines are the twelve fields in its dialog.

    The order of the precondition lines is the order of the dialog fields. Put the parameters in the order a user would think about them: the battery size first, then the clearances and thicknesses, then the hole pattern. The holder does exactly that.

    Ids and the Context

    Every operation in a feature has an id, and every query that refers to an operation's result uses that id. Ids are hierarchical, they must be children of the feature's id, and their order must reflect the order operations were created. Get the ids right and queries resolve; get them wrong and operations throw CANNOT_RESOLVE_ENTITIES.

    Ids

    An Id identifies a feature or operation in a context. Ids are hierarchical: the root is newId(), and children are built with +. Internally an Id is an array of strings.

    FEATURESCRIPT
    var baseId = id + "base";            // a child of the feature's id
var sketchId = id + "baseSketch";     // another child
var topId = makeId("Top");            // an id built from a string
var any = ANY_ID;                     // the "*" wildcard

    Within a feature, operation ids must be children of the feature's id, and the id hierarchy must reflect contiguous creation history. That last rule has a sharp edge in loops: id + "extrude" + i in a loop fails on the second iteration, because the second id is not a contiguous continuation of the first. Use id + i + "extrude" instead, so the loop index comes before the name. makeId("Top") builds an id from a string, which is how you refer to the standard planes, and ANY_ID is the "*" wildcard.

    The Context

    A Context is a builtin storing modeling data: bodies, entities, variables, and feature error states. Every Part Studio uses a single Context, and all features, operations, and evaluation functions require one. Each context records the standard-library version it was created at, so a feature held back to an older version emulates old behaviour.

    You can attach your own variables to the context, shared between features:

    FEATURESCRIPT
    setVariable(context, "foo", 1);
var foo = getVariable(context, "foo");   // 1

    Context variables are also reachable in a Part Studio as #foo. There are query-valued versions too: getQueryVariable and setQueryVariable. The holder does not use context variables; its values are computed from the definition and passed along as ordinary variables. That is the normal pattern for a single feature, and it keeps the feature self-contained.

    The general operation contract

    An operation takes (context, id, definition), modifies the context, and returns undefined. It can fail by throwing, or report warnings and infos that are readable through the getFeature... functions. When an operation parameter that requires one entity receives a query resolving to multiple entities, it takes the first. That rule is worth remembering when a query is broader than you intended: the operation will not complain, it will silently use the first match.

    Parameters with bounds: LengthBoundSpec

    A length parameter in a dialog is not just a number field. It has a minimum, a default, and a maximum, and a default for each unit system the user might be working in. A LengthBoundSpec is how you declare all of that in one place.

    The pattern

    FEATURESCRIPT
    annotation { "Name" : "Battery length (REV: 113.5)" }
isLength(definition.batteryLength, { (millimeter) : [50, 113.5, 200] } as LengthBoundSpec);

    The map has one entry per unit. The first unit listed defines the minimum value, the default value, and the maximum value, in terms of that unit; the subsequent units define default values for those units. The docs' canonical form lists several units:

    FEATURESCRIPT
    const MY_LENGTH_BOUNDS =
{
    (meter) : [-500, 0.0025, 500],
    (centimeter) : .25,
    (millimeter) : 2.50,
    (inch) : 0.1,
    (foot) : 0.01,
    (yard) : 0.0025
} as LengthBoundSpec;

    The default value for a unit that is not listed is the default value of the first unit, so { (inch): [0, 1, 1e4]} as LengthBoundSpec gives a default of 2.54 cm in a Part Studio with centimeter units. The holder uses the millimeter-only form, which is a valid instantiation of the same pattern: one unit, carrying the minimum, default, and maximum. The UI-spec example in the docs is the same shape with a different first unit: isLength(definition.myLength, { (inch) : [ 0, 1.75, 10000 ] } as LengthBoundSpec);.

    The typecheck for a bound spec is canBeLengthBoundSpec(value). There are analogous specs for the other dimensions: AngleBoundSpec (for example (degree): [0, 30, 360], with a (radian) default), IntegerBoundSpec (for example (unitless): [1, 2, 1e5]), and RealBoundSpec (for example (unitless): [0, 1, 1e5]).

    The library ships ready-made bound specs for the common cases, so you do not have to write { (millimeter) : ... } for every parameter:

{

    The header and import are the same two lines as the holder.     Sketches: newSketchOnPlane and skSolve

    A sketch is a two-dimensional drawing on a plane, and it is the raw material for almost every solid in a feature. The workflow is always the same: create the sketch, add entities to it, and solve it. Nothing you draw exists in the Part Studio until skSolve runs.

    The workflow

    FEATURESCRIPT
    var sketch1 = newSketchOnPlane(context, id + "sketch1",
        { "sketchPlane" : plane(vector(0, 0, 0) * inch, vector(0, 0, 1)) });
skCircle(sketch1, "circle1", { "center" : vector(0, 0) * inch, "radius" : 1 * inch });
skSolve(sketch1);

    Sketch inputs are usually 2D Vectors relative to the sketch plane's origin and x-axis. To convert a projected 3D point into sketch coordinates, use worldToPlane(Plane, Vector). Constraints may be added, but the docs say they are almost always unnecessary, since you already have the ability to place the entities precisely where you intend them to be. That is the normal way to work in FeatureScript: compute the coordinates and place the entities exactly, instead of drawing loosely and constraining afterwards.

    After skSolve, all sketch edges become WIRE bodies, enclosed regions become SURFACE bodies, and vertices that are not edge endpoints, such as skPoint points and skCircle centres, become POINT bodies. That is why a sketch region can be extruded: the enclosed region is a real surface body in the context, and qSketchRegion can find it.

    FEATURESCRIPT
    // Top and bottom edges

skLineSegment(sketch, prefix ~ "bottom", { "start" : pt(xl, -halfW), "end" : pt(-xl, -halfW) });

    Each arc's mid point sits at 45 degrees, offset by r * 0.70710678 from the corner, so the arc connects the end of one edge to the start of the next and the loop closes.     Sketch points and the is2dPoint rule

    This is the rule that bit the battery holder three times, and it is the single most important rule in this guide. A sketch point must be a 2D length vector: a vector with length units on every component. A bare number anywhere in it fails, and passing lengths straight into vector() does not satisfy the rule either.

    The rule

    is2dPoint(value) is "True for a single 2D length Vector", and its documented example is vector(0.5, 1) * inch. The companion predicate isLengthVector is "True for a Vector where all members are values with length units". So a 2D length vector requires length units on every component:

    FEATURESCRIPT
    vector(0.5, 1) * inch          // a 2D length vector: satisfies is2dPoint
vector(0, 0)                    // unitless: fails is2dPoint
vector(0, 1 * inch)             // a bare 0 mixed with a length: fails is2dPoint
vector(0, 0, 0) * inch          // 3D: fails is2dPoint (it is not 2D)

    The second and third lines are the traps. A bare 0 is not a length, so a vector containing one is not a length vector, even if the other component has units. And a 3D vector is not a 2D point, even with units everywhere. The precondition failure you get names the rule: for skPoint, the reported error is "Precondition of skPoint failed (value.position is undefined || is2dPoint(value.position))".

    What the docs do and do not say. The is2dPoint definition is in the FsDoc, and the is2dPoint precondition is visible in reported errors for skPoint and for skRegularPolygon ("is2dPoint(value.center)"). But the skCircle table in the FsDoc does not print an is2dPoint precondition for its center field: it lists center as a Vector with the example vector(0, 0) * inch. This guide teaches the rule from the is2dPoint definition, not from skCircle's table, because that is where the docs actually state it. In practice, treat every sketch point as a 2D length vector, whichever sk function takes it.

    The pt() idiom

    The reliable way to build a sketch point from computed lengths is the documented idiom vector(number, number) * unit: divide each length by a unit to get plain numbers, build the vector from the numbers, and multiply the vector back by the unit. The holder wraps it in a helper and uses it for every sketch point in the file:

    FEATURESCRIPT
    // Builds a 2D sketch point from two lengths, using the documented idiom
// vector(number, number) * unit. Never pass lengths straight into vector() —
// the result does not satisfy is2dPoint and skCircle rejects it.
function pt(x is ValueWithUnits, y is ValueWithUnits)
{
    return vector(x / millimeter, y / millimeter) * millimeter;
}

const zero = 0 * millimeter;   // a zero that is a length, for centers on an axis

    Passing lengths straight into vector(), as in vector(hx, hy), does not satisfy is2dPoint, and skCircle rejects the center with a precondition failure. The zero constant exists for the same reason: a hole centre on an axis needs a length zero, and a bare 0 is not one. Direction vectors such as vector(0, 0, 1) are unitless by design and are fine as they are; the rule applies to points, not directions.

    Use the helper everywhere, even where a literal would work. vector(0, 0) * inch is fine as a literal, but the moment a coordinate becomes a computed value, the helper is the form that keeps working. The holder's six hole centres are the proof: three of them use zero for the y-coordinate, and all six go through pt.

    Constraints: usually you don't need them

    In a Part Studio you draw loosely and constrain afterwards. In FeatureScript you usually do the opposite: compute the coordinates and place each entity exactly, and skip constraints entirely. The docs say constraints "may be added, but are almost always unnecessary, since you already have the ability to place the entities precisely where you intend them to be."

    skConstraint

    BoundingType has seven values: BLIND, UP_TO_NEXT, UP_TO_SURFACE, UP_TO_BODY, UP_TO_VERTEX, THROUGH_ALL, and UP_TO_FACE. A blind bound is a fixed depth; the up-to bounds stop at the next entity, a named surface, a named body, a vertex, or a face; through-all goes through everything.

    There is no operationType field on opExtrude. Read the field list above again: it is not there. That field belongs to the native extrude feature, which does the boolean for you afterwards.     Tools, targets, and keepTools

    In a SUBTRACTION, the tools are the bodies being removed and the targets are the bodies being cut from. The tools are consumed by default: after the subtraction, the tool body is gone.     Queries: selecting entities

    An operation never names a body directly. It takes a query, and the query describes which entities it means. A query is a value you build, combine, and pass around, and it only resolves to actual entities when something evaluates it against the context.

    What a Query is

    A Query is a map with a queryType (a QueryType) and an optional entityType (an EntityType). It holds criteria, not an entity list. There are two kinds: state-based queries, which describe the entities as they are now, and historical queries, which describe entities by how they came to be. qCreatedBy is a historical query: it finds entities by the operation that created them.

    FEATURESCRIPT
    var bodies = evaluateQuery(context, qCreatedBy(id + "base", EntityType.BODY));
// bodies is an array of transient queries, one per entity

    evaluateQuery(context, query) returns an array of transient queries, one per entity the query matched. The order is arbitrary, except for qUnion, where earlier subqueries come first. Evaluated queries may become invalid if the context is modified after they are evaluated, so evaluate late, close to where you use the result.

    Three helpers go with it: evaluateQueryCount counts the matches without returning them, isQueryEmpty tests whether a query matches nothing, and areQueriesEquivalent tests whether two queries match the same entities.

    EntityType values

    EntityType has four values: VERTEX, EDGE, FACE, and BODY. They are the filter you pass to queries that take one, such as qCreatedBy(id + "base", EntityType.BODY), which finds only the bodies created by the base extrude, not the sketch regions or wires the same operation may have touched. BodyType is a related enum with six values: SOLID, SHEET, WIRE, POINT, MATE_CONNECTOR, and COMPOSITE. It describes what kind of body something is, and qBodyType filters by it.

    Combining queries

    Queries compose. qUnion matches entities matching any subquery, and it is the only combinator that guarantees order: earlier subqueries come first. qSubtraction matches entities in the first query but not the second, preserving the first query's order. qIntersection matches entities in all subqueries, preserving the first subquery's order. qSymmetricDifference matches entities in exactly one of two queries. The holder's unions are built with qUnion over an array, and the order of that array is load-bearing: the main body comes first, so the merged result keeps its identity.

    Identity: who created that body?

    A query like qCreatedBy(id + "base", EntityType.BODY) only works if you know what "created by" means after booleans have merged and split bodies. The rule is precise, and it is narrower than the battery holder's own comments claim. This chapter states the documented rule, and says plainly where the holder's comments overstate it.

    The documented rule

    qCreatedBy is "a query for all the entities created by a feature or operation". An entity is "created by" an operation if the entity was added to the context as part of that operation. Entities modified, but not created, by an operation are not returned. Two consequences follow for booleans:

    • Split entities are "created by" both the original creator and the split operation.
    • Merged entities are "created by" the creators of each merged entity as well as the merging operation itself.

    The second point is the one that matters. A merged UNION result is created by the merging operation too, which means it can be found with qCreatedBy using the boolean operation's own id. That contradicts the blanket claim in the holder file's comments, that a boolean result can never be found with qCreatedBy(booleanOpId). The blanket claim is wrong as a general statement, and this guide does not repeat it.

    What is actually safe to rely on

    The UNION identity rule from the opBoolean entry is documented separately and is safe: "When several bodies merge, the identity of the tool that appears earliest in the query is preserved (in particular, body color and body name are taken from it)." So if the base is listed first in a union, the merged result keeps the base's identity, and qCreatedBy(id + "base", EntityType.BODY) finds it.

    For a SUBTRACTION, the docs do not state that the result keeps the target's identity. That reading is consistent with the qCreatedBy rule, since a subtraction target is modified, not created, by the operation, but it is an inference, not a documented sentence. Treat it as a reasonable expectation to verify in a Feature Studio, not as a documented guarantee.

    The cases where the "never" conclusion does hold are the non-merging ones: a UNION of disjoint tools that do not touch keeps each tool's own creation, so no merged body exists to find by the boolean's id, and a SUBTRACTION target is modified rather than created. The holder's practice, tracking the main body by its original creation id through the whole feature and listing it first in every union, is the safe practice in every case: it works whether or not the merged result is also findable by the boolean's id. What the file's comment gets wrong is presenting that safe practice as if the alternative were impossible. It is not impossible; it is merely not the practice the file relies on.

    Why the file tracks by the base id anyway. The holder was written after an actual failure: querying a boolean result by the boolean's own id resolved to nothing, and opBoolean threw CANNOT_RESOLVE_ENTITIES. Tracking by the original creation id fixed it. The documented qCreatedBy rule says a merged result should also be findable by the merging operation, so the observed failure and the doc text do not fully agree. The test chapter asks you to check this in Onshape, because the Feature Studio is the authority where the docs and an observed failure disagree.

    The practice, in one paragraph

    Give the first solid you create a clear id, such as id + "base". Refer to the main body by that id for the rest of the feature. List the main body first in every union, so the merged result keeps its identity. Never rely on a boolean's own id to find its result, and never rely on a subtraction target keeping its identity without testing it. If a query resolves to nothing, check the identity first: it is the most common reason a boolean throws CANNOT_RESOLVE_ENTITIES.

    Three traps the holder teaches

    The holder file carries its history in its comments: each of its three traps bit an earlier version of the file, and each one is a rule from the earlier chapters, learned the hard way. Read them here once, and you will recognize them in your own features before they bite you.

    1. Sketch points must be 2D length vectors

    The first version of the file passed computed lengths straight into vector(), as in vector(hx, hy), and used bare 0 for centres on an axis. skCircle rejected the centres with a precondition failure, because the result does not satisfy is2dPoint: a sketch point needs length units on every component, and a bare 0 is not a length. The fix is the pt() helper from the sketch-points chapter, used for every sketch point in the file, plus a length-valued zero constant for axis centres. Direction vectors such as vector(0, 0, 1) are unitless by design and are unaffected.

    2. opExtrude has no operationType

    The first version passed "operationType" : NewBodyOperationType.REMOVE to opExtrude, expecting the extrude to cut. That field belongs to the native extrude feature, not to the op, and opExtrude silently ignores it. The enum's values are NEW, ADD, REMOVE, and INTERSECT; the extras chapter lists them with the other body-creation enums. The "cuts" came out as extra solid blocks and regeneration failed. The fix used in the file is explicit booleans: extrude each cut profile as a new tool body, then subtract it with opBoolean and BooleanOperationType.SUBTRACTION, and merge with BooleanOperationType.UNION where bodies join. The silence is the lesson: an unknown field in an operation's definition map is ignored, not rejected, so a misspelled or misplaced field fails downstream instead of at the line where you wrote it.

    3. Boolean identity is narrower than the file's comments claim

    The file's comments say that after a UNION the result keeps the identity of the tool that appears earliest in the query, and after a SUBTRACTION it keeps the target's identity, so a boolean result can never be found with qCreatedBy(booleanOpId). The first clause is documented. The second clause is not stated in the docs as read; it is an inference from the qCreatedBy rule that modified entities are not returned. And the "never" conclusion is wrong as a blanket statement: the qCreatedBy entry says merged entities are "created by" the creators of each merged entity as well as the merging operation itself, so a merged UNION result can be found through the boolean's own id.

    What the file actually relies on is the safe practice, and the safe practice is correct: track the main body by its original creation id, qCreatedBy(id + "base"), and list it first in every union. That works in every case, whether or not the merged result is also findable by the boolean's id. The comment overstates the rule; the practice does not depend on the overstatement. The test chapter gives you a small experiment that settles the question in a Feature Studio, where the docs and an observed failure disagree.

    Two things to confirm first

    One experiment, for the identity question

    The docs and an observed failure disagree about whether a merged UNION result can be found with qCreatedBy using the boolean's own id. Settle it with a small experiment feature: two overlapping boxes, merged with a UNION, and then debug the query for the boolean's id.

    FEATURESCRIPT
    FeatureScript 3112;
import(path : "onshape/std/common.fs", version : "3112.0");

function pt(x is ValueWithUnits, y is ValueWithUnits)
{
    return vector(x / millimeter, y / millimeter) * millimeter;
}

annotation { "Feature Type Name" : "Identity Experiment" }
export const identityExperiment = defineFeature(function(context is Context, id is Id, definition is map)
    precondition
    {
        annotation { "Name" : "Box size" }
        isLength(definition.size, { (millimeter) : [5, 10, 50] } as LengthBoundSpec);
    }
    {
        const s = definition.size;
        var sk1 = newSketchOnPlane(context, id + "sk1", {
                "sketchPlane" : plane(vector(0, 0, 0) * millimeter, vector(0, 0, 1))
            });
        skRectangle(sk1, "r1", { "firstCorner" : pt(-s, -s), "secondCorner" : pt(s, s) });
        skSolve(sk1);
        opExtrude(context, id + "box1", {
                "entities" : qSketchRegion(id + "sk1"),
                "direction" : vector(0, 0, 1),
                "endBound" : BoundingType.BLIND,
                "endDepth" : s
            });
        var sk2 = newSketchOnPlane(context, id + "sk2", {
                "sketchPlane" : plane(vector(0, 0, 1) * (s / 2), vector(0, 0, 1))
            });
        skRectangle(sk2, "r2", { "firstCorner" : pt(0 * millimeter, -s), "secondCorner" : pt(2 * s, s) });
        skSolve(sk2);
        opExtrude(context, id + "box2", {
                "entities" : qSketchRegion(id + "sk2"),
                "direction" : vector(0, 0, 1),
                "endBound" : BoundingType.BLIND,
                "endDepth" : s
            });
        opBoolean(context, id + "merge", {
                "tools" : qUnion([qCreatedBy(id + "box1", EntityType.BODY), qCreatedBy(id + "box2", EntityType.BODY)]),
                "operationType" : BooleanOperationType.UNION
            });
        debug(context, qCreatedBy(id + "merge", EntityType.BODY));
    });

    debug(context, query) highlights the entities the query finds in red while the dialog is open. If the merged body highlights, the boolean's id finds it, and the docs' wording is the behaviour. If nothing highlights, the boolean's id does not find it, and the observed failure is the behaviour. Either way, report what you see: it decides whether the holder file's comment needs a correction, or a confirmation.     Debugging: println, debug, and reading errors

    A feature that fails gives you three tools: console output, entity highlighting, and the error message itself. Used together, they answer the only two debugging questions that matter: what value did this actually have, and which entities did this query actually find.

    Printing values

    FEATURESCRIPT
    println("cavity length: " ~ toString(cavityL));
print("no newline here");
eprintln("an error-stream message");

    println, print, and eprintln write to the console, and toString converts a value to a string. ~ concatenates. Print a derived dimension when a sketch looks wrong: if the printed value is not the one you expected, the bug is in the arithmetic, not in the sketch. Remove the prints before you finish, or leave one or two that explain a surprising value; a feature that prints on every regeneration is noisy in a large Part Studio.

    Highlighting entities

    debug(context, query) highlights the entities a query finds in red while the dialog is open. It is the fastest way to answer "did this query find what I think it found". The identity experiment in the test chapter uses it to check whether a boolean's id finds a merged body. Use it the same way whenever a boolean throws CANNOT_RESOLVE_ENTITIES: debug the tools query and the targets query separately, and the empty one is the broken one.

    To inspect geometry rather than identity, the evaluation functions read values out of the context: evBox3d for a bounding box, evDistance, evPlane, evLength, evVolume, evArea, evApproximateCentroid, evApproximateMassProperties, evVertexPoint, evLine, and evFaceTangentPlanes for planes tangent to a face at parameter-space points. Print the result of one of these when a dimension looks wrong: it tells you what the part actually measures, not what the code intended.

    FEATURESCRIPT
    // REV Slim Battery Holder — Onshape FeatureScript
// ============================================================
// A protective 3D-printable slide-in sleeve for the REV Robotics 12V Slim
// Battery (REV-31-1302, 12 V 3000 mAh NiMH).
//
// Battery size is taken straight from REV's product page
// (https://www.revrobotics.com/rev-31-1302/):
//   Maximum Dimensions: 113.5 mm x 90.5 mm x 23 mm
// The cavity adds 2 mm of padding per side (117.5 x 94.5 mm) so the pack
// drags in and out freely instead of wedging.
//
// HOW IT WORKS
// - The +X end is open: the battery slides/drags in from that end along the
//   base, and the XT30 lead exits through the same open end (inline 20 A fuse
//   sits outside the holder).
// - Two lips along the top of the long walls overhang the battery by 2 mm per
//   side and sit 1 mm above its top, so the pack cannot lift out — it can only
//   slide in and out the open end. The walls are 26 mm above the base (taller
//   than the 23 mm battery) so the lips clear the pack.
// - Six M4 mounting holes (diameter 4.2 mm clearance) at (+/-72, -32 / 0 / +32),
//   a 144 x 64 mm pattern where every hole lands on the goBILDA 8 mm grid.
// - The base is a flat tray; the holder is hollow all the way through — the
//   cavity is open at the top between the lips and open at the +X end.
//
// HOW TO USE
// 1. In Onshape, open the document where the holder should live and create a
//    Feature Studio (right-click a tab > "Create Feature Studio", or + > Feature Studio).
// 2. Paste this whole file into the Feature Studio.
// 3. In a Part Studio, open the custom-feature dropdown in the feature toolbar
//    and pick "REV Slim Battery Holder". It builds the holder centred on the
//    origin, on the Top plane, base running from Z = 0 up.
// 4. Print in PETG or ASA: 3 walls, 4 top/bottom layers, ~30% infill.
//    Mount with M4 bolts to a goBILDA plate — align the holder centre to a
//    grid hole on the plate and the six holes line up.
// 5. Slide the battery in from the open (+X) end. To remove it, pull it back
//    out by the end of the pack (or its lead).
//
// FEATURESCRIPT NOTES (from the Onshape Standard Library docs, cad.onshape.com/FsDoc)
// - Header + import: FeatureScript 3112 with onshape/std/common.fs 3112.0.
// - Sketches: newSketchOnPlane + skRectangle / skCircle / skLineSegment / skArc,
//   then skSolve. A sketch plane can be an offset plane, e.g.
//   plane(vector(0, 0, 1) * (3 * millimeter), vector(0, 0, 1)).
// - Solids: opExtrude with "entities" : qSketchRegion(...),
//   "direction" : vector(0, 0, 1), "endBound" : BoundingType.BLIND,
//   "endDepth" : <length>. opExtrude always creates NEW bodies.
// - SKETCH POINTS — READ THIS, it bit the file three times: a sketch point
//   must be a 2D *length* vector, and the only reliable way to build one from
//   computed lengths is the documented idiom vector(number, number) * unit
//   (the is2dPoint example is vector(0.5, 1) * inch). Passing lengths
//   straight into vector(), as in vector(hx, hy), does NOT satisfy
//   is2dPoint — skCircle rejects the center with a precondition failure, and
//   a bare 0 is not a length either. This file therefore builds every sketch
//   point through the pt() helper below, which divides the lengths by
//   millimeter to plain numbers and multiplies the vector back by millimeter.
//   Direction vectors such as vector(0, 0, 1) are unitless by design and are
//   fine as they are.
// - IMPORTANT (this bit the first version): opExtrude does NOT take an
//   "operationType" field — that field belongs to the native `extrude`
//   *feature*, which does the boolean for you afterwards. Passing
//   "operationType" : NewBodyOperationType.REMOVE to opExtrude is silently
//   ignored, so the "cuts" came out as extra solid blocks and regeneration
//   failed. The fix used here is explicit booleans: extrude each cut profile
//   as a new tool body, then opBoolean with
//   "operationType" : BooleanOperationType.SUBTRACTION (tools = tool body,
//   targets = main body), and opBoolean UNION to merge the base, walls,
//   and lips into one body.
// - Identity gotcha (this bit the boolean version): after an opBoolean UNION
//   the result keeps the identity of the tool that appears earliest in the
//   query, and a SUBTRACTION keeps the target's identity — so a boolean
//   result can NEVER be found with qCreatedBy(booleanOpId); that query
//   resolves to nothing and opBoolean throws CANNOT_RESOLVE_ENTITIES. The
//   main body is therefore tracked through the whole feature by its original
//   creation id, qCreatedBy(id + "base"), with the main body listed first in
//   every UNION so the identity stays "base".
// - Lengths are ValueWithUnits (there is no `Length` type — `isLength` is only
//   a predicate for parameter checks). Parameters use isLength with
//   { (millimeter) : [min, default, max] } as LengthBoundSpec.
//
// HONEST LIMITS
// - This was written and checked against the docs, but NOT run inside Onshape
//   (no Feature Studio access here). If Onshape flags a line, the error will
//   name the exact operation; the step numbers in the comments map 1:1 to the
//   build order, so the failing step is easy to find. If it still fails, send
//   the exact error text from the feature and it will point at the step.
// - Battery dims are REV's published maxima (113.5 x 90.5 x 23 mm). The cavity
//   has 2 mm padding per side for sliding; if your pack's shrink wrap measures
//   larger, or the slide feels too loose/tight, adjust "Clearance per side"
//   in the feature dialog.
// - The slide fit depends on print accuracy: if the lips print with elephant's
//   foot or the walls bow inward, the pack may bind — a first print in PLA for
//   a fit check is cheaper than going straight to PETG/ASA.

// Builds a 2D sketch point from two lengths, using the documented idiom
// vector(number, number) * unit. Never pass lengths straight into vector() —
// the result does not satisfy is2dPoint and skCircle rejects it.
function pt(x is ValueWithUnits, y is ValueWithUnits)
{
    return vector(x / millimeter, y / millimeter) * millimeter;
}

// Adds a rounded-rectangle outline (4 lines + 4 arcs) to a sketch.
// halfL / halfW are the half length / half width, r the corner radius.
function roundedRectOutline(sketch is Sketch, prefix is string, halfL is ValueWithUnits, halfW is ValueWithUnits, r is ValueWithUnits)
{
    const xl = halfL - r;
    const yw = halfW - r;
    const d = r * 0.70710678; // 45-degree offset for the arc midpoints

    // Top and bottom edges
    skLineSegment(sketch, prefix ~ "top", { "start" : pt(-xl, halfW), "end" : pt(xl, halfW) });
    skLineSegment(sketch, prefix ~ "bottom", { "start" : pt(xl, -halfW), "end" : pt(-xl, -halfW) });
    // Right and left edges
    skLineSegment(sketch, prefix ~ "right", { "start" : pt(halfL, yw), "end" : pt(halfL, -yw) });
    skLineSegment(sketch, prefix ~ "left", { "start" : pt(-halfL, -yw), "end" : pt(-halfL, yw) });

    // Corner arcs: start, mid (45 deg), end. Each arc connects the end of one
    // edge to the start of the next, so the loop is closed.
    skArc(sketch, prefix ~ "arcTR", { "start" : pt(halfL, yw), "mid" : pt(xl + d, yw + d), "end" : pt(xl, halfW) });
    skArc(sketch, prefix ~ "arcBR", { "start" : pt(xl, -halfW), "mid" : pt(xl + d, -yw - d), "end" : pt(halfL, -yw) });
    skArc(sketch, prefix ~ "arcBL", { "start" : pt(-halfL, -yw), "mid" : pt(-xl - d, -yw - d), "end" : pt(-xl, -halfW) });
    skArc(sketch, prefix ~ "arcTL", { "start" : pt(-xl, halfW), "mid" : pt(-xl - d, yw + d), "end" : pt(-halfL, yw) });
}

annotation { "Feature Type Name" : "REV Slim Battery Holder" }
export const revSlimBatteryHolder = defineFeature(function(context is Context, id is Id, definition is map)
    precondition
    {
        annotation { "Name" : "Battery length (REV: 113.5)" }
        isLength(definition.batteryLength, { (millimeter) : [50, 113.5, 200] } as LengthBoundSpec);
        annotation { "Name" : "Battery width (REV: 90.5)" }
        isLength(definition.batteryWidth, { (millimeter) : [50, 90.5, 200] } as LengthBoundSpec);
        annotation { "Name" : "Battery height (REV: 23)" }
        isLength(definition.batteryHeight, { (millimeter) : [10, 23, 50] } as LengthBoundSpec);
        annotation { "Name" : "Clearance per side (slide padding)" }
        isLength(definition.clearance, { (millimeter) : [0, 2, 5] } as LengthBoundSpec);
        annotation { "Name" : "Wall thickness" }
        isLength(definition.wallThickness, { (millimeter) : [1.5, 3, 6] } as LengthBoundSpec);
        annotation { "Name" : "Base thickness" }
        isLength(definition.baseThickness, { (millimeter) : [2, 3, 6] } as LengthBoundSpec);
        annotation { "Name" : "Wall height above base" }
        isLength(definition.wallHeight, { (millimeter) : [5, 26, 40] } as LengthBoundSpec);
        annotation { "Name" : "Lip overhang into cavity" }
        isLength(definition.lipOverhang, { (millimeter) : [0, 4, 10] } as LengthBoundSpec);
        annotation { "Name" : "Lip thickness" }
        isLength(definition.lipThickness, { (millimeter) : [1, 2, 4] } as LengthBoundSpec);
        annotation { "Name" : "Mounting hole diameter" }
        isLength(definition.holeDiameter, { (millimeter) : [4, 4.2, 5] } as LengthBoundSpec);
        annotation { "Name" : "Hole spacing along length" }
        isLength(definition.holeSpacingX, { (millimeter) : [32, 144, 200] } as LengthBoundSpec);
        annotation { "Name" : "Hole spacing across width" }
        isLength(definition.holeSpacingY, { (millimeter) : [32, 64, 160] } as LengthBoundSpec);
    }
    {
        // Derived dimensions (defaults in mm):
        // cavity 117.5 x 94.5, walls outer 123.5 x 100.5, base 160 x 106.5,
        // total height 29 (3 base + 26 wall). Battery top sits at Z = 26,
        // lips run Z = 27..29, so there is 1 mm of slide clearance above it.
        const cavityL = definition.batteryLength + 2 * definition.clearance;
        const cavityW = definition.batteryWidth + 2 * definition.clearance;
        const wallOuterL = cavityL + 2 * definition.wallThickness;
        const wallOuterW = cavityW + 2 * definition.wallThickness;
        // Base overhangs the walls by one wall thickness on the long sides and
        // leaves 8 mm past each mounting hole at the ends.
        const baseL = definition.holeSpacingX + 16 * millimeter;
        const baseW = wallOuterW + 2 * definition.wallThickness;
        const totalH = definition.baseThickness + definition.wallHeight;
        const cornerR = 4 * millimeter;
        const zero = 0 * millimeter;

        // 1. Base plate: rounded rectangle, 3 mm thick, on the Top plane. ----
        var baseSketch = newSketchOnPlane(context, id + "baseSketch", {
                "sketchPlane" : plane(vector(0, 0, 0) * millimeter, vector(0, 0, 1))
            });
        roundedRectOutline(baseSketch, "base", baseL / 2, baseW / 2, cornerR);
        skSolve(baseSketch);
        opExtrude(context, id + "base", {
                "entities" : qSketchRegion(id + "baseSketch"),
                "direction" : vector(0, 0, 1),
                "endBound" : BoundingType.BLIND,
                "endDepth" : definition.baseThickness
            });

        // 2. Wall block: solid rectangle extruded the full height. It overlaps
        //    the base (Z 0-3); the two are merged in step 3. ------------------
        var wallSketch = newSketchOnPlane(context, id + "wallSketch", {
                "sketchPlane" : plane(vector(0, 0, 0) * millimeter, vector(0, 0, 1))
            });
        skRectangle(wallSketch, "wallRect", {
                "firstCorner" : pt(-wallOuterL / 2, -wallOuterW / 2),
                "secondCorner" : pt(wallOuterL / 2, wallOuterW / 2)
            });
        skSolve(wallSketch);
        opExtrude(context, id + "walls", {
                "entities" : qSketchRegion(id + "wallSketch"),
                "direction" : vector(0, 0, 1),
                "endBound" : BoundingType.BLIND,
                "endDepth" : totalH
            });

        // 3. Merge base + walls into one body. Per the opBoolean docs, when
        //    bodies merge the result keeps the identity of the tool that
        //    appears earliest in the query — here the base — so every later
        //    step keeps referring to the main body as qCreatedBy(id + "base").
        //    Querying a boolean result by the boolean's own id finds nothing
        //    (CANNOT_RESOLVE_ENTITIES); never do that. -------------------------
        opBoolean(context, id + "mergeBaseWalls", {
                "tools" : qUnion([qCreatedBy(id + "base", EntityType.BODY), qCreatedBy(id + "walls", EntityType.BODY)]),
                "operationType" : BooleanOperationType.UNION
            });

        // 4. Battery cavity tool: the hollow the battery slides into, extruded
        //    as its own solid from the top of the base (Z = 3) up through the
        //    top of the walls. --------------------------------------------------
        var cavitySketch = newSketchOnPlane(context, id + "cavitySketch", {
                "sketchPlane" : plane(vector(0, 0, 1) * definition.baseThickness, vector(0, 0, 1))
            });
        skRectangle(cavitySketch, "cavityRect", {
                "firstCorner" : pt(-cavityL / 2, -cavityW / 2),
                "secondCorner" : pt(cavityL / 2, cavityW / 2)
            });
        skSolve(cavitySketch);
        opExtrude(context, id + "cavityTool", {
                "entities" : qSketchRegion(id + "cavitySketch"),
                "direction" : vector(0, 0, 1),
                "endBound" : BoundingType.BLIND,
                "endDepth" : definition.wallHeight
            });

        // 5. Subtract the cavity tool from the main body (still identified
        //    as the base — a SUBTRACTION keeps the target's identity). --------
        opBoolean(context, id + "cutCavity", {
                "tools" : qCreatedBy(id + "cavityTool", EntityType.BODY),
                "targets" : qCreatedBy(id + "base", EntityType.BODY),
                "operationType" : BooleanOperationType.SUBTRACTION
            });

        // 6. Open-end tool: removes the +X end wall above the base so the
        //    battery can slide/drag in from that end (and the XT30 lead can
        //    exit there). The tool also takes the last 4 mm of the long walls
        //    at the entry, which acts as a lead-in. The base stays, so the
        //    pack slides in along it. -------------------------------------------
        var openSketch = newSketchOnPlane(context, id + "openSketch", {
                "sketchPlane" : plane(vector(0, 0, 1) * definition.baseThickness, vector(0, 0, 1))
            });
        skRectangle(openSketch, "openRect", {
                "firstCorner" : pt(cavityL / 2 - 1 * millimeter, -wallOuterW / 2 - 1 * millimeter),
                "secondCorner" : pt(wallOuterL / 2 + 2 * millimeter, wallOuterW / 2 + 1 * millimeter)
            });
        skSolve(openSketch);
        opExtrude(context, id + "openTool", {
                "entities" : qSketchRegion(id + "openSketch"),
                "direction" : vector(0, 0, 1),
                "endBound" : BoundingType.BLIND,
                "endDepth" : definition.wallHeight
            });

        // 7. Subtract the open-end tool from the main body. --------------------
        opBoolean(context, id + "cutOpenEnd", {
                "tools" : qCreatedBy(id + "openTool", EntityType.BODY),
                "targets" : qCreatedBy(id + "base", EntityType.BODY),
                "operationType" : BooleanOperationType.SUBTRACTION
            });

        // 8. Retaining lips: two strips along the top of the long walls that
        //    overhang the cavity by lipOverhang, at the very top of the walls
        //    (Z = totalH - lipThickness .. totalH). They sit 1 mm above the
        //    battery top, so the pack can slide under them but cannot lift out.
        var lipSketch = newSketchOnPlane(context, id + "lipSketch", {
                "sketchPlane" : plane(vector(0, 0, 1) * (totalH - definition.lipThickness), vector(0, 0, 1))
            });
        skRectangle(lipSketch, "lipPlus", {
                "firstCorner" : pt(-wallOuterL / 2, cavityW / 2 - definition.lipOverhang),
                "secondCorner" : pt(wallOuterL / 2, wallOuterW / 2)
            });
        skRectangle(lipSketch, "lipMinus", {
                "firstCorner" : pt(-wallOuterL / 2, -wallOuterW / 2),
                "secondCorner" : pt(wallOuterL / 2, -(cavityW / 2 - definition.lipOverhang))
            });
        skSolve(lipSketch);
        opExtrude(context, id + "lipTools", {
                "entities" : qSketchRegion(id + "lipSketch"),
                "direction" : vector(0, 0, 1),
                "endBound" : BoundingType.BLIND,
                "endDepth" : definition.lipThickness
            });

        // 9. Merge the lips into the main body. The main body is listed first
        //    in the union so the result keeps the base identity. ---------------
        opBoolean(context, id + "mergeLips", {
                "tools" : qUnion([qCreatedBy(id + "base", EntityType.BODY), qCreatedBy(id + "lipTools", EntityType.BODY)]),
                "operationType" : BooleanOperationType.UNION
            });

        // 10. M4 mounting-hole tools: 6 cylinders, diameter 4.2 mm (clearance
        //     for M4 bolts) at (+/-72, -32 / 0 / +32) — a 144 x 64 mm pattern
        //     where every hole lands on the goBILDA 8 mm grid. Extruded from
        //     the Top plane through the 3 mm base only. --------------------------
        var holeSketch = newSketchOnPlane(context, id + "holeSketch", {
                "sketchPlane" : plane(vector(0, 0, 0) * millimeter, vector(0, 0, 1))
            });
        const hx = definition.holeSpacingX / 2;
        const hy = definition.holeSpacingY / 2;
        const hr = definition.holeDiameter / 2;
        skCircle(holeSketch, "hole1", { "center" : pt(hx, hy), "radius" : hr });
        skCircle(holeSketch, "hole2", { "center" : pt(hx, zero), "radius" : hr });
        skCircle(holeSketch, "hole3", { "center" : pt(hx, -hy), "radius" : hr });
        skCircle(holeSketch, "hole4", { "center" : pt(-hx, hy), "radius" : hr });
        skCircle(holeSketch, "hole5", { "center" : pt(-hx, zero), "radius" : hr });
        skCircle(holeSketch, "hole6", { "center" : pt(-hx, -hy), "radius" : hr });
        skSolve(holeSketch);
        opExtrude(context, id + "holeTools", {
                "entities" : qSketchRegion(id + "holeSketch"),
                "direction" : vector(0, 0, 1),
                "endBound" : BoundingType.BLIND,
                "endDepth" : definition.baseThickness
            });

        // 11. Subtract the hole tools from the main body. ----------------------
        opBoolean(context, id + "cutHoles", {
                "tools" : qCreatedBy(id + "holeTools", EntityType.BODY),
                "targets" : qCreatedBy(id + "base", EntityType.BODY),
                "operationType" : BooleanOperationType.SUBTRACTION
            });
    });
