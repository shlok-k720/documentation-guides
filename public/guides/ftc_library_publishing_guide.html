Creating and Publishing FTC Libraries

This guide takes you from a new Android Studio project to a real FTC library that another team can add to TeamCode with two lines in Gradle: a pure-logic module and an Android module that talks to the FTC SDK, written mainly in Java with Kotlin compiling alongside it in both modules, built with Kotlin DSL Gradle scripts, and published free with JitPack.

Who this is for. You already write Java for FTC, you have used a library from Gradle (Pedro Pathing, FTC Dashboard, or similar), and you want to stop copy-pasting the same code between robots or share a controller, a localizer helper, or a tuner with other teams. You do not need to know Gradle deeply. You do need Android Studio, a GitHub account, and a test Quickstart you are willing to break.

What you will finish with

By the end you will have a public GitHub repository containing the running example from this guide, a first tagged release, and a JitPack coordinate that resolves in a clean Quickstart clone. The example is deliberately small so that every moving part is visible:

example-core

A pure Java/Kotlin JAR. A slew-rate limiter and its config type. No Android, no FTC SDK, unit-tested on your computer.

example-ftc

An Android library (AAR). A motor controller that wraps a DcMotor and uses the core limiter. It compiles against the FTC SDK but does not bundle it.

A JitPack release

One tag, v0.1.0, that any TeamCode can consume as com.github.yourname.FtcExampleLib:example-ftc:v0.1.0 after adding the JitPack repository.

The example is not trying to be the best slew-rate limiter ever written. It is trying to be the smallest library that exercises every decision a real library has to make: two modules, two languages, compileOnly dependencies, publishing metadata, a consumer test, and a release. Once those decisions are in place, swapping in your own controller, geometry, or tuner is mostly a matter of writing more classes in the same shape.

How to use this guide

  1. Read sequentially the first time. The chapters build on each other in the order you would actually do the work: setup, modules, code, local test, JitPack, on-robot check, iteration.
  2. Build the example as you read. Every step assumes Android Studio: menus to click, fields to fill, and settings to set. Every build file in the guide is shown in full. The reference chapter near the end collects them in one place so you can copy them without hunting back through the text.
  3. Replace the placeholders everywhere, every time. yourname, FtcExampleLib, and com.example.ftclib are placeholders. A half-replaced example is the most common reason a first JitPack build fails, and the troubleshooting chapters assume you searched for all three.
  4. Verify locally before you tag. JitPack builds from a tag. A tag is cheap to create and awkward to fix. The local mavenLocal() test in the middle of the guide exists so your first tag is boring.

What this guide deliberately does not cover

There is no Maven Central chapter. That is a deliberate choice for this guide, not a claim that Maven Central is bad: Pedro Pathing publishes there, and it is the right home for a widely used library. But it needs namespace verification, GPG signing, and complete POM metadata, which is a second guide's worth of setup. JitPack is free, needs no account or signing, and is how Aarav Dhawan's FtcAutoTune is published. Start there. If your library outgrows JitPack, the module structure, the maven-publish setup, and the versioning discipline in this guide all carry over.

There is also no chapter on writing your own dashboard, web tuner, or OpMode-scanning framework. Those are libraries built on top of this shape. Get the shape right first, with one small, honest feature.

Versions move. Every version in this guide was checked on 1 November 2026 against the real repositories named in the text. FTC SDK, Pedro Pathing, AGP, Gradle, and Kotlin all release on their own schedules. Where a version is a rule (“match your Quickstart”) the guide says so. Where a version is an example pin, check the Quickstart you actually use before copying it blindly.

What an FTC library actually is

An FTC library is not a special kind of program. It is a normal JVM/Android library, packaged the way Gradle already knows how to package libraries, that happens to depend on the FTC SDK only while it is being compiled.

The two packages: JAR and AAR

PackageMade byContainsUsed for
JARjava-library pluginCompiled .class files, plus resourcesPure logic: math, geometry, controllers, parsing. No Android APIs.
AARcom.android.library pluginCompiled classes, an Android manifest, resources, and assetsAnything that touches Android or the FTC SDK: OpMode helpers, hardware wrappers, dashboards, assets.

Both are just zip files with metadata. When TeamCode declares implementation on your library, Gradle downloads the JAR or AAR, puts its classes on the compile classpath, and merges the AAR's manifest and resources into the robot app at build time. Your library never runs as a separate app. There is no separate install step on the Control Hub, and no separate process. If you can explain that sentence to someone, the rest of this guide is details.

Why two modules: core and ftc

This guide, Aarav's FtcAutoTune, and Pedro Pathing all use the same split, for the same three reasons:

  • Testability. Pure logic in core can be unit-tested with plain JUnit on your computer, in seconds, with no robot, no Android emulator, and no hardware map. Logic trapped inside an Android module can only be tested slowly, or not at all.
  • Reuse. A core JAR can be used by a desktop simulator, a dashboard, a test harness, or a future non-Android consumer. An AAR cannot.
  • Build speed and clarity. The Android module is the slow, fiddly part of the build. Keeping it thin — wrappers, lifecycle, hardware access — and pushing decisions into core keeps both modules honest about what they depend on.
core (JAR, pure Java/Kotlin)→ftc (AAR, Android + FTC SDK)→TeamCode (robot app)

The arrow points one way. ftc depends on core. core never depends on ftc, never imports com.qualcomm.robotcore, and never imports anything from android.*. If you catch yourself wanting an FTC type inside core, that is the design telling you the FTC part belongs in a wrapper in ftc, with the decision in core expressed in plain numbers.

compileOnly: the most important dependency word in this guide

The FTC SDK is already in the robot app. The Quickstart's FtcRobotController module brings RobotCore, Hardware, and friends. Your library must compile against those APIs, but it must not bundle a second copy of them into its AAR. That is what compileOnly means:

KOTLIN DSL
// In ftc/build.gradle.kts. Compiles against the SDK; does not ship it.
compileOnly("org.firstinspires.ftc:RobotCore:11.1.0")
compileOnly("org.firstinspires.ftc:Hardware:11.1.0")

If you use implementation for the FTC SDK instead, Gradle will happily build your library, and the consumer will get duplicate SDK classes, version conflicts, or a mysteriously larger APK. The build may even succeed and then misbehave on the robot. Treat any implementation line naming org.firstinspires.ftc in a library as a bug until proven otherwise. The same rule applies to any dependency the host app already provides: compile against it, do not ship it.

api vs implementation, in one paragraph each

  • api means “consumers of my library will also see this dependency.” example-ftc declares api(project(":core")) because TeamCode code calls core types through the FTC wrapper. If core were implementation, TeamCode could not name those types without adding core itself.
  • implementation means “only my code uses this; consumers do not need it on their compile classpath.” Use it for helpers that never appear in your public API. It keeps consumers' builds faster and their classpaths cleaner.

Getting this backwards is not fatal, but it leaks. An implementation dependency that appears in a public method signature will produce “cannot access class” errors for consumers, with the error pointing at their code. When in doubt, ask: “Does a caller need to name this type to use my API?” If yes, api. If no, implementation.

What about a single-module library? If your library is pure logic with no FTC types at all, one core-style JAR module is enough. If it touches hardware or OpModes, it needs the Android module. What you should not do is put everything in one Android module “for simplicity”: you lose fast unit tests and you force every consumer, including desktop tools, to take an Android dependency for pure math.

Set up Android Studio, the JDK, and Gradle

A library project needs the same tools as a robot project, plus one discipline: the JDK that runs Gradle and the Java version your code targets are two different settings, and confusing them is the most common setup failure in this guide.

Install Android Studio and API 30

  1. Install Android Studio. Open it once and let first-run setup finish.
  2. Open the SDK Manager. Click Tools → SDK Manager.
  3. Install API 30. On the SDK Platforms tab, tick Android 11.0 (R), API 30. Click Apply, then OK.
  4. Leave the SDK location alone. It is machine-specific. Do not commit local.properties.

Set Gradle JDK to 17

  1. Open Settings. Click File → Settings. On a Mac, click Android Studio → Settings.
  2. Open the Gradle settings. Click Build, Execution, Deployment → Build Tools → Gradle.
  3. Pick JDK 17. In Gradle JDK, choose a JDK 17. If none is listed, install JDK 17 first, then click Add JDK and pick it.
  4. Apply and sync. Click OK, then click Sync Now in the banner.

Gradle runs on JDK 17. Your code still targets Java 8: the build files set that. Confusing the two is the most common setup failure in this guide.

To check, open the Terminal tab at the bottom, type the command below, and confirm the version starts with 17.

BASH
java -version

Three clicks this guide uses

  1. Sync Now. After editing a build file, click Sync Now in the banner at the top of the editor.
  2. Gradle tool window. Click View → Tool Windows → Gradle. Double-click a task to run it. A step that says “run” a task means this, unless it names the Terminal tab.
  3. Replace a file. Double-click the file in the Project view, select all, paste the block from this guide, then click Sync Now.

If a step names a file, find it in the Project view. Switch the view dropdown at the top of the Project view to Project if the folders are hidden.

Gradle with Kotlin DSL

Every build script in this guide is Kotlin DSL: build.gradle.kts and settings.gradle.kts. That is a deliberate choice, and it is the only build-script language this guide teaches. Groovy DSL appears only where the consumer Quickstart requires it — in the consumer chapters and the reference chapter — because the FTC Quickstart itself is written in Groovy.

Why Kotlin DSL for the library

  • It matches the projects you are copying. FtcAutoTune and Pedro Pathing both use .kts build files. Copying their patterns into Groovy files is a translation exercise with no benefit.
  • It is statically typed. Android Studio offers completion and shows type errors in a .kts file as you type. A Groovy build script fails at runtime, often halfway through a build, with an error that names the wrong line.
  • It is the same language as half your code. If Kotlin is going to compile in both modules anyway, writing the build in Kotlin keeps one language for “how it builds” and “what it does.”
Do not mix DSLs in one project. A project with build.gradle in one module and build.gradle.kts in another will confuse both Gradle and every future reader. Pick Kotlin DSL for the whole library repo and convert any snippet you copy from a Groovy example before pasting it in. The syntax differences are small and the failures from mixing them are not.

How to read a .kts build file

A Kotlin DSL build file is Kotlin code that Gradle executes to configure a project. Three idioms cover almost everything in this guide:

IdiomWhat it meansExample
plugins { ... }Declare the plugins this module uses, with versions in the root project only.id("com.android.library")
Function-call blocksandroid { ... } configures the Android extension. The block is a lambda configuring an object.android { namespace = "..." }
String function callsDependencies are function calls with a string coordinate, not assignments.compileOnly("org.firstinspires.ftc:RobotCore:11.1.0")

Two details catch Java programmers out. First, backticks: `java-library` and `maven-publish` are written in backticks because their names contain a hyphen, which is not a valid Kotlin identifier. That is normal Kotlin DSL, not a typo. Second, assignment vs function call: namespace = "..." sets a property, while compileOnly("...") calls a function. If Android Studio underlines a line, check which of the two you meant before changing the version number.

Groovy vs Kotlin DSL, side by side

So you can translate anything you find in the wild, here is the same dependency in both languages. The library uses the Kotlin version. The consumer Quickstart uses the Groovy version, because that is how the Quickstart is written.

KOTLIN DSL
dependencies {
    api(project(":core"))
    compileOnly("org.firstinspires.ftc:RobotCore:11.1.0")
    compileOnly("org.firstinspires.ftc:Hardware:11.1.0")
}
GROOVY
dependencies {
    implementation 'com.github.yourname.FtcExampleLib:example-ftc:v0.1.0'
}

Notice what did not change: the coordinate string group:artifact:version is identical in both languages. Only the surrounding syntax differs. When you copy a coordinate from a README, copy the string inside the quotes and rewrite the wrapper in your own DSL.

Where versions live

This guide puts plugin versions in the root build.gradle.kts (with apply false) and dependency versions inline in the module that uses them, following FtcAutoTune's shape. A version catalog (gradle/libs.versions.toml, as Pedro Pathing uses) is a fine upgrade once you have more than two modules or more than one library sharing versions. It is not needed for a first library, and it adds a file whose syntax you would have to learn before you have written any library code. Start explicit, catalog later if the duplication hurts.

Versions that must match the robot

Most first-library build failures are not code failures. They are version disagreements between the library, the Quickstart, and the build tools. This chapter is the complete list of disagreements to check, in the order to check them.

Rule 1: compileSdk must not exceed the consumer's compileSdk

A library compiled against API 35 cannot be consumed by an app compiled against API 30. The app's compiler does not know the newer APIs the library was compiled against, and the build fails with errors about missing symbols or a compileSdk mismatch. A library compiled against API 30 can be consumed by an app compiled against API 34 or 35. So the safe choice is the lowest compileSdk that provides the APIs you actually use — usually the Quickstart's own compileSdk.

Find the consumer's value before you choose yours. In a Quickstart, look in build.common.gradle (older) or the module build.gradle (newer) for compileSdk / compileSdkVersion. FtcAutoTune uses 30 because the Quickstart it targeted used 30. Pedro's current revhub and tuning modules use 35 because their target Quickstarts moved on. Copy the number from your consumer, and write down where you found it, in a comment or in the README.

compileSdk is not the Android version on the robot. It is the API level the code is compiled against. The FTC SDK supports back to API 24, which is why minSdk is 24, regardless of whether you compile against 30 or 35. Compiling against a newer API does not make old devices run newer code; it only lets you call newer APIs, which will then fail at runtime on old devices if you actually call them. Keep compileSdk low and do not call APIs above the device's level.

Rule 2: minSdk is 24, target is Java 8

The FTC SDK floor is API 24. Set minSdk = 24 in the ftc module and do not raise it to “modernize” the library; you would exclude the very devices the library is for. For bytecode, set Java sourceCompatibility and targetCompatibility to VERSION_1_8, and the Kotlin jvmTarget to JVM_1_8, in both modules. All three must agree. A Kotlin class compiled to a newer bytecode version than the Java classes around it will fail with an “unsupported class file” style error that looks like a Gradle bug and is not.

Rule 3: FTC SDK version must match the Quickstart

compileOnly dependencies are resolved at library compile time against the version you declare, and at runtime against the version the app ships. If those differ, you can compile against a method that does not exist at runtime, or miss a method that does. The rule is simple: declare the same FTC SDK version the consuming Quickstart declares. Check it in the Quickstart's build.dependencies.gradle (or wherever that Quickstart centralizes dependencies) and copy the version number exactly. The example uses 11.1.0 because that is what FtcAutoTune's build declares. If your Quickstart is on 12.0.0, change all three FTC lines (RobotCore, Hardware, and FtcCommon if you use it) together. Never mix 11.1.0 and 12.0.0 in one module.

Rule 4: AGP, Gradle, JDK, and Kotlin move together

PairExample in this guideIf it disagrees
AGP ↔ GradleAGP 8.7.0 ↔ Gradle 8.9Gradle refuses to run, or AGP features are missing. Check the AGP compatibility table for your AGP version.
AGP ↔ JDKAGP 8.7 ↔ JDK 17Gradle fails to start, or JitPack builds with JDK 8 by default and fails. Pin JDK 17 in jitpack.yml.
Kotlin plugin ↔ stdlibBoth 2.1.20Duplicate or conflicting stdlib classes. Use kotlin("stdlib") so the version follows the plugin.
Kotlin ↔ AGP/GradleKotlin 2.1.20 with AGP 8.7 / Gradle 8.9Kotlin compilation fails or the Android plugin cannot find the Kotlin plugin. Upgrade Kotlin and AGP together, never alone.

When you upgrade one of these, upgrade the set and re-run the local test in the consuming-locally chapters before tagging. A “small” AGP bump that you do not test locally becomes a JitPack build failure that you debug through a web log, which is a much worse place to debug.

How to check a version exists before you depend on it

Before you declare any coordinate, confirm the artifact exists at that version in the repository you expect. For Maven Central artifacts, fetch the maven-metadata.xml for the artifact (for example, https://repo1.maven.org/maven2/org/firstinspires/ftc/RobotCore/maven-metadata.xml) and confirm your version is listed. For JitPack artifacts, the equivalent check is the JitPack build log for that tag, covered in the JitPack chapters. Do not guess a version number from a blog post, a video, or memory. Version numbers that do not exist produce “could not resolve” errors that look identical to network errors, and you will waste an hour checking your network.

Where source lives, and why Kotlin files live in a java folder

Both modules keep source under src/main/java/..., even for .kt files. That is not a mistake. When the Kotlin Gradle plugin is applied, it treats src/main/java as a joint source directory: Java and Kotlin files in the same directory are compiled together, in the right order, with each language able to see the other's declarations. A separate src/main/kotlin directory also works, but splitting languages into different folders makes the “both languages compile together” story harder to see and adds a second place to look for every feature. Keep one source root per module, one package tree, two file extensions.

The same applies to tests: src/test/java/... holds both .java and .kt test files in the core module. The ftc module has no unit-test source set in this example, because its logic is kept thin enough to live in core. If you later add Android-dependent tests, they belong in src/test with Robolectric or in src/androidTest on a device — both are beyond the scope of a first library, and the guide says so rather than pretending otherwise.

Coordinates, groups, and packages

A library has four different names, and confusing them causes half the “it works locally but JitPack cannot find it” reports. Keep them separate in your head, even though they often look similar.

NameExampleWhere it is setWhat it controls
Groupcom.github.yourname.FtcExampleLibgradle.properties (GROUP)For JitPack, this is fixed: com.github.<user>.<repo>. You do not choose it freely.
Artifactexample-core, example-ftcEach module's publishing blockWhich module's output a consumer gets. One repo, one group, one artifact per module.
Versionv0.1.0 (tag)The git tag, and VERSION_NAME in gradle.propertiesWhich release a consumer gets. On JitPack, the tag is the version.
Package / namespacecom.example.ftclib.core; namespace com.example.ftclib.ftcSource file package lines; Android namespaceHow code names your classes, and (for Android) how resources are namespaced. Independent of the Maven group.

A consumer writes the coordinate as one string: group:artifact:version. For the example FTC module that is com.github.yourname.FtcExampleLib:example-ftc:v0.1.0. Read it left to right: whose repo, which module, which release. If any of the three is wrong, Gradle's error will say the artifact was not found, and it will not tell you which part was wrong. Check them in that order.

The JitPack group is not a choice

On Maven Central you claim a namespace — io.github.yourname, or a domain you own — and the group is yours to use across many projects. On JitPack there is no claiming step. The group is mechanically derived from the repository: com.github.<GitHub username>.<repository name>, with the username and repository name exactly as they appear in the URL, including capitalization. FtcAutoTune's group is com.github.aaravdhawan25.FtcAutoTune because the repo is aaravdhawan25/FtcAutoTune. If you rename the repository, the group changes, and every consumer must update their dependency. Choose the repository name as if it were part of the public API, because on JitPack it is.

Packages: stable, boring, and yours

The Java/Kotlin package is the name callers write in import statements. It should be stable across versions, boring, and clearly yours. The example uses com.example.ftclib, which is a placeholder in the same spirit as example.com in documentation: replace com.example with a reverse domain you control, such as com.github.yourname or your team's domain. Do not ship a real library under com.example; it will collide with every other tutorial project on earth.

The Android namespace (set in the ftc module's android block) should match the FTC module's package root. It namespaces generated resources and the manifest. It does not have to equal the Maven group, and in this example it deliberately does not: the group is GitHub-derived, the namespace is package-derived. Keeping that distinction explicit in the build files, with a comment, saves the next maintainer from “fixing” one to match the other.

Use lowercase, hyphenated artifact names that say what the module is: example-core and example-ftc, following FtcAutoTune's pidautotuner-core and pidautotuner-ftc. What each part is doing

  • java-library + kotlin("jvm"). The Java plugin provides the JAR, the source sets, and the java component. The Kotlin JVM plugin adds Kotlin compilation to the same source sets, so .java and .kt files under src/main/java compile together. Neither plugin alone gives you both languages.

Write the core in Java: SlewRateLimiter

The core feature is a slew-rate limiter: given a requested output, it returns an output that moves toward the request no faster than a configured rate. It is the kind of small, pure, testable logic that belongs in core — no hardware, no time source it cannot be given, no hidden state that cannot be reset.

The Java class

Put this file at core/src/main/java/com/example/ftclib/core/SlewRateLimiter.java. Read the constructor and the calculate method first; everything else is support for those two decisions.

JAVA
package com.example.ftclib.core;

/**
 * Limits how fast an output value may change.
 *
 * <p>On each call to {@link #calculate(double, double)}, the returned value moves
 * from the previous output toward {@code target} by at most
 * {@code maxChangePerSecond * dtSeconds}. This smooths step changes in a
 * requested motor power without hiding the target from the caller: the caller
 * always knows the target, and this class only decides how fast to approach it.
 *
 * <p>This class keeps no clock of its own. The caller supplies {@code dtSeconds},
 * so tests can drive it with exact time steps and robot code can supply the
 * real loop period. Call {@link #reset(double)} when the mechanism is
 * re-homed or the controller is disabled, so the next output starts from a
 * known value instead of a stale one.
 */
public final class SlewRateLimiter {

    private final double maxChangePerSecond;
    private final double minOutput;
    private final double maxOutput;
    private double previousOutput;

    /** Creates a limiter with explicit bounds. */
    public SlewRateLimiter(LimiterConfig config) {
        this(config.getMaxChangePerSecond(), config.getMinOutput(), config.getMaxOutput(),
                config.getInitialOutput());
    }

    /** Creates a limiter from plain numbers, for callers who do not use the config type. */
    public SlewRateLimiter(double maxChangePerSecond, double minOutput, double maxOutput,
            double initialOutput) {
        if (!(maxChangePerSecond > 0.0)) {
            throw new IllegalArgumentException("maxChangePerSecond must be positive");
        }
        if (minOutput > maxOutput) {
            throw new IllegalArgumentException("minOutput must not exceed maxOutput");
        }
        this.maxChangePerSecond = maxChangePerSecond;
        this.minOutput = minOutput;
        this.maxOutput = maxOutput;
        this.previousOutput = clamp(initialOutput, minOutput, maxOutput);
    }

    /**
     * Returns the next output, moved toward {@code target} by at most
     * {@code maxChangePerSecond * dtSeconds}, then clamped to the output bounds.
     */
    public double calculate(double target, double dtSeconds) {
        if (!(dtSeconds >= 0.0)) {
            throw new IllegalArgumentException("dtSeconds must not be negative");
        }
        double clampedTarget = clamp(target, minOutput, maxOutput);
        double maxChange = maxChangePerSecond * dtSeconds;
        double change = clamp(clampedTarget - previousOutput, -maxChange, maxChange);
        previousOutput = clamp(previousOutput + change, minOutput, maxOutput);
        return previousOutput;
    }

    /** Resets the limiter so the next output starts from {@code value}. */
    public void reset(double value) {
        previousOutput = clamp(value, minOutput, maxOutput);
    }

    /** Returns the most recent output, without advancing the limiter. */
    public double getPreviousOutput() {
        return previousOutput;
    }

    private static double clamp(double value, double min, double max) {
        return Math.max(min, Math.min(max, value));
    }
}

API decisions worth copying

  • Time is a parameter, not a clock. The limiter takes dtSeconds instead of reading System.nanoTime() or an FTC ElapsedTime. That single decision makes the class testable with exact steps, reusable in a simulator with a different clock, and honest about its one assumption: the caller knows how much time passed. Any pure-logic class that secretly reads the clock is harder to test and harder to trust.
  • Fail fast on bad configuration. The constructor rejects a non-positive rate and inverted bounds with IllegalArgumentException, at construction time, with a message naming the bad value's rule. A limiter constructed with a zero rate would silently never move; a limiter constructed with inverted bounds would clamp everything to nonsense. Fail at construction, in plain language, and the bug is found where it was made.
  • Two constructors, one implementation. The config-based constructor delegates to the numbers-based one. Callers who like a config object use it; callers who want four numbers use those. Neither path duplicates validation or clamping logic. When you add a Kotlin config type in the next chapter, this delegation is what lets Java and Kotlin callers share one implementation.
  • Final class, private state, no static mutable state. A limiter is stateful by nature — it remembers the previous output — so each mechanism gets its own instance. There is deliberately no singleton, no static registry, and no global “the limiter.” Two mechanisms sharing one limiter instance would corrupt each other's state in a way that looks like a tuning problem and is actually an aliasing problem.

What is deliberately not in this class

There is no feedforward, no PID, no voltage compensation, and no hardware access. Those are separate decisions with separate tests. A library that tries to be a complete controller in its first class will be hard to explain, hard to test, and hard to change. The limiter does one thing, does it with exact time steps, and leaves the rest to the caller or to a second, equally small class. If your own library's first class is already doing three things, split it before you publish it. Splitting after publication is a breaking change; splitting before publication is just editing.

/**
 * Configuration for [SlewRateLimiter].
 *
 * @property maxChangePerSecond the fastest the output may move, in output units per second.
 * @property minOutput the lowest output the limiter may return.
 * @property maxOutput the highest output the limiter may return.
 * @property initialOutput the output the limiter starts from, clamped to the bounds.

What the Kotlin plugin actually added

  • A joint compile. Gradle compiles Kotlin and Java together in one task graph, so Kotlin can see Java declarations and Java can see Kotlin declarations in the same module, without a separate source set or a build ordering hack. If you split them into src/main/java and src/main/kotlin, the same joint compile still happens — the split only changes where you look.
  • The stdlib. The Kotlin plugin makes kotlin-stdlib available. The build file declares it explicitly as api(kotlin("stdlib")) so consumers get it transitively, because a Kotlin type is now part of the public API. The kotlin("stdlib") notation means “the stdlib version matching this plugin version.” Do not hard-code a different stdlib version alongside a Kotlin plugin version; that is how duplicate-stdlib errors start.
  • Nullability information. Kotlin's type system records nullability in the compiled class files. Java callers see it as annotations, Kotlin callers see it as types. The interop chapter explains how to write Kotlin so Java callers cannot accidentally pass null where Kotlin expects a value — and what happens when they do it anyway.

Calling Kotlin from Java, and Java from Kotlin

The Java limiter calls the Kotlin config through ordinary getters: config.getMaxChangePerSecond(). From Kotlin, the same property is accessed as config.maxChangePerSecond, with no getter call written out. Both spellings refer to the same property. The data class also gives Kotlin callers copy(), equals(), hashCode(), and toString() for free; Java callers get the same methods, spelled as ordinary method calls, plus a copy(...) method with all four parameters that Java callers should generally avoid in favor of constructing a new config.

Default arguments need a note of their own. Kotlin callers can write LimiterConfig(2.0) and get the defaults for the other three properties. Java callers cannot use Kotlin default arguments; they must pass all four arguments, or use the numbers-based SlewRateLimiter constructor. That asymmetry is normal, and the API-design chapter explains the two standard fixes (@JvmOverloads, and a Java-friendly overload) and when each is worth it. For a config type with four properties, the numbers-based Java constructor in the previous chapter is already the Java-friendly path, so no annotation is needed here. Do not add annotations to fix a problem that an overload already solved.

A Java test for the limiter

Put this file at core/src/test/java/com/example/ftclib/core/SlewRateLimiterTest.java. JAVA
package com.example.ftclib.core;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertThrows;

import org.junit.jupiter.api.Test;

class SlewRateLimiterTest {

    @Test
    void movesAtMostTheAllowedAmountPerStep() {
        SlewRateLimiter limiter = new SlewRateLimiter(1.0, -1.0, 1.0, 0.0);
        assertEquals(0.1, limiter.calculate(1.0, 0.1), 1e-9);
        assertEquals(0.2, limiter.calculate(1.0, 0.1), 1e-9);
    }

    @Test
    void reachesTheTargetGivenEnoughTime() {
        SlewRateLimiter limiter = new SlewRateLimiter(1.0, -1.0, 1.0, 0.0);
        double output = 0.0;
        for (int i = 0; i < 20; i++) {
            output = limiter.calculate(0.5, 0.1);
        }
        assertEquals(0.5, output, 1e-9);
    }

    @Test
    void clampsToBoundsAndRejectsBadConfig() {
        SlewRateLimiter limiter = new SlewRateLimiter(10.0, -0.5, 0.5, 0.0);
        assertEquals(0.5, limiter.calculate(1.0, 1.0), 1e-9);
        assertEquals(-0.5, limiter.calculate(-1.0, 1.0), 1e-9);
        assertThrows(IllegalArgumentException.class,
                () -> new SlewRateLimiter(0.0, -1.0, 1.0, 0.0));
    }

    @Test
    void resetStartsFromTheGivenValue() {
        SlewRateLimiter limiter = new SlewRateLimiter(1.0, -1.0, 1.0, 0.0);
        limiter.calculate(1.0, 0.1);
        limiter.reset(0.0);
        assertEquals(0.0, limiter.getPreviousOutput(), 1e-9);
    }
}

Write the FTC wrapper in Java

The FTC wrapper's job is translation, not decision-making. It takes a DcMotor from the hardware map, takes a target power from OpMode code, and uses the core limiter to decide what power to actually set. All of the “how fast may it change” logic lives in core. All of the “which motor, which direction, which mode” knowledge lives here.

The Java wrapper

Put this file at ftc/src/main/java/com/example/ftclib/ftc/ExampleMotorController.java.

JAVA
package com.example.ftclib.ftc;

import com.example.ftclib.core.LimiterConfig;
import com.example.ftclib.core.SlewRateLimiter;
import com.qualcomm.robotcore.hardware.DcMotor;
import com.qualcomm.robotcore.hardware.DcMotorSimple;

/**
 * Drives one motor with slew-rate-limited power.
 *
 * <p>This class owns no timing and no OpMode lifecycle. The caller must call
 * {@link #update(double)} once per loop with the elapsed time since the
 * previous call, and must call it from the OpMode loop — not from a
 * constructor, not from a background thread, and not after the OpMode stops.
 *
 * <p>The motor is configured for open-loop power control:
 * {@link DcMotor.RunMode#RUN_WITHOUT_ENCODER}. If you need encoder-based
 * velocity control, use a different wrapper; do not silently change this
 * class's run mode behind the caller's back.
 */
public final class ExampleMotorController {

    private final DcMotor motor;
    private final SlewRateLimiter limiter;
    private double targetPower;

    /** Creates a controller for {@code motor} with the given limiter config. */
    public ExampleMotorController(DcMotor motor, LimiterConfig config) {
        if (motor == null) {
            throw new IllegalArgumentException("motor must not be null");
        }
        this.motor = motor;
        this.limiter = new SlewRateLimiter(config);
        this.motor.setMode(DcMotor.RunMode.RUN_WITHOUT_ENCODER);
        this.motor.setZeroPowerBehavior(DcMotor.ZeroPowerBehavior.BRAKE);
        this.motor.setPower(0.0);
    }

    /** Creates a controller with a plain rate limit and motor-power bounds. */
    public ExampleMotorController(DcMotor motor, double maxChangePerSecond) {
        this(motor, new LimiterConfig(maxChangePerSecond, -1.0, 1.0, 0.0));
    }

    /** Sets the desired power. The limiter decides how fast the motor approaches it. */
    public void setTargetPower(double targetPower) {
        this.targetPower = targetPower;
    }

    /**
     * Advances the limiter by {@code dtSeconds} and writes the resulting
     * power to the motor. Call once per OpMode loop iteration.
     */
    public void update(double dtSeconds) {
        double power = limiter.calculate(targetPower, dtSeconds);
        motor.setPower(power);
    }

    /** Stops the motor and resets the limiter, so the next start is from zero. */
    public void stop() {
        targetPower = 0.0;
        limiter.reset(0.0);
        motor.setPower(0.0);
    }

    /** Returns the power most recently written to the motor. */
    public double getAppliedPower() {
        return limiter.getPreviousOutput();
    }

    /** Sets the motor direction. Prefer setting direction in the hardware config when possible. */
    public void setDirection(DcMotorSimple.Direction direction) {
        motor.setDirection(direction);
    }
}

Decisions in this wrapper worth copying

  • Constructor takes hardware, not a hardware map. The wrapper receives an already-looked-up DcMotor. It does not call hardwareMap.get(), does not know the motor's configuration name, and cannot be constructed before the hardware map exists. That keeps the wrapper testable in principle (a fake DcMotor could be passed in a test harness) and keeps configuration-name knowledge in exactly one place: the OpMode that owns the hardware map.
  • Configuration happens once, in the constructor, visibly. Run mode, zero-power behavior, and initial power are set where the reader can see them, and nowhere else. A wrapper that reconfigures the motor on every update() call, or that changes run mode in response to a setter, will surprise the caller at the worst possible moment — mid-match, when the motor suddenly behaves differently.
  • update(dt), not a thread, not a clock. Like the core limiter, the wrapper takes elapsed time as a parameter. FTC OpModes are single-threaded loops; a wrapper that spawns its own thread to write motor powers introduces races with the OpMode loop and with OpMode stop. Keep the wrapper synchronous, call it from the loop, and let the OpMode own the loop period.
  • stop() is a first-class operation. Stopping is not “set target to zero and wait for the limiter.” It zeroes the target, resets the limiter, and writes zero immediately. When an OpMode stops, or a mechanism is disabled, the caller should not have to reason about how long the limiter will take to wind down. Make the safe thing the easy thing, and name it stop().

What the wrapper does not do

It does not read gamepads, does not write telemetry, does not decide what the target power should be, and does not know about other mechanisms. Those are OpMode responsibilities. A wrapper that writes telemetry on every update will flood the Driver Station and slow the loop; a wrapper that reads gamepads cannot be reused in autonomous. If you want telemetry, expose getAppliedPower() (as here) and let the OpMode decide what to display. The boundary is: the library moves the motor; the OpMode decides why.

Why @JvmOverloads is here, and what it costs

Kotlin default arguments do not exist in Java. A Java caller looking at this constructor without @JvmOverloads would see exactly one constructor, requiring both arguments, and would have no way to use the default config. @JvmOverloads tells the Kotlin compiler to also generate the Java-friendly overloads — in this case, a one-argument constructor that supplies the default config. The cost is one extra generated constructor and a slightly larger class file. For a public API type that Java callers will construct directly, that cost is worth paying. For an internal type that only Kotlin code constructs, it is not. The interop chapter gives the full decision rule; the short version is: annotate the public constructors Java callers will actually use, and leave internal ones alone.

Kotlin property access on FTC types

Notice motor.power = 0.0 and motor.direction = direction. Kotlin treats a Java getter/setter pair as a property, so getPower()/setPower() become power, and getDirection()/setDirection() become direction. This is convenient and it is also a trap for readers: motor.power = 0.0 writes to hardware. It is not assigning a field. When you read Kotlin FTC code, treat every property assignment on a hardware type as a hardware write, and keep such assignments in obvious places — constructors and update() methods — not buried in property initializers or getters.

An Android library needs a manifest. It does not need resources, activities, or a launcher icon. Most first libraries ship exactly one manifest and zero resources, and that is correct.

Include it anyway: an explicit manifest is clearer than relying on AGP to synthesize one, and it gives you a place to declare permissions or components later, when you actually need them. (FtcAutoTune's ftc module ships no manifest at all and builds on JitPack; the empty manifest here is the explicit version of the same choice.) Pedro Pathing’s revhub manifest is the same single empty element.

Add manifest entries only when a feature requires them, and document each one in the README so consumers are not surprised by a permission prompt they did not ask for.

Resources: only if you have them

Android library resources live in ftc/src/main/res/: layouts, drawables, strings, values. The example has none, and that is fine — AGP does not require a res folder. Add resources only when a feature genuinely needs them, such as a dashboard layout or a bundled image. When you do, remember three rules:

  • Prefix every resource name. Library resources share a namespace with the app's resources at build time. A layout named activity_main in a library will collide with the app's own activity_main. Prefix with your library name: example_dashboard, not dashboard.
  • Do not ship a launcher icon or an app theme. Those belong to the app. A library theme that overrides the app's theme will change the look of every consumer's Driver Station UI in ways they did not consent to.
  • Keep resources minimal. Every resource in the AAR is merged into the consumer's APK. Unused resources cost build time and APK size for every team that depends on you, forever, until you remove them in a breaking release.

Assets: how files ship inside the AAR

Files under ftc/src/main/assets/ are packaged into the AAR unchanged and are readable at runtime through the app's AssetManager (via a Context). This is how libraries ship bundled web UIs, default configuration files, or model files — FtcAutoTune, for example, ships its dashboard HTML as an asset inside the ftc module. Two cautions apply:

  • Assets are not resources. They have no generated R constants, no compile-time checking, and no type safety. A misspelled asset path fails at runtime, on the robot, when the code tries to open it. Keep asset paths in one constant, and test the open path in the on-robot chapter.
  • Assets are read-only at runtime. Do not write back to an asset path, do not treat assets as a database, and do not expect changes to an asset file to persist across app restarts. If a feature needs writable storage, it needs a files directory and a Context, which the library should receive as a parameter — not conjure from a static holder.

The example ships no assets. If you add a dashboard later, add the asset, add the constant for its path, and add the on-robot check that opens it. In that order.

OpModes: ship them, or template them?

This is the one design decision in this guide where both options are used by real libraries, and the wrong choice for your library will annoy every consumer. The example ships no OpModes in the library. Here is why, and when you should do the opposite.

How OpMode discovery works, briefly

The FTC SDK discovers OpModes by scanning classes in the app (including library AARs) for @TeleOp / @Autonomous annotations at startup. That means a @TeleOp class inside your library will appear on the Driver Station, with no action by the team beyond adding the dependency. That is convenient for a tuner or a demo, and it is the reason FtcAutoTune's library contains a dashboard toggle OpMode: run it once, and a setting persists.

It is also the reason shipped OpModes are a liability for most libraries. Every OpMode you ship appears in every consumer's OpMode list, forever, with the name you chose. If a team copies your example OpMode into TeamCode (as they should, to configure it for their robot), they now have two OpModes with similar names. If you rename a shipped OpMode in a later release, teams that built muscle memory around the old name lose it. If a shipped OpMode assumes a hardware name that does not exist on a team's robot, it will fail at init in a way that looks like the team's fault.

The template pattern: copy it, own it

The pattern FtcAutoTune uses for its tuners — and the pattern this guide recommends for configurable OpModes — is: the library ships the logic (the master/controller classes), and the team copies thin OpMode + config files into TeamCode and edits them for their robot. The copied files are theirs. They can rename them, change hardware names, adjust targets, and delete them without affecting the library. The library never has to guess a team's hardware names.

For the example, the template is one OpMode and no config file is needed, because the hardware name and rate are the only configuration and both fit in the OpMode itself. The full template is in the test-Quickstart chapter, where it is used for real. Its shape is worth stating here, because it is the contract between library and team:

  • Thin. The OpMode creates the controller, sets a target from the gamepad or a constant, calls update(dt) in the loop, and stops the controller on exit. All decision logic is in the library.
  • Owned by the team. The file lives in org.firstinspires.ftc.teamcode, in the team's repo, under the team's control. The library never updates it, renames it, or depends on it.
  • Safe by default. The template starts stopped, uses a low rate, and requires the driver to hold a button or press start deliberately before the motor moves. A template that moves a mechanism the moment it is initialized is a safety bug, not a convenience.

When shipping an OpMode is the right choice

Ship an OpMode in the library when it needs no per-team configuration and its whole purpose is to be run as-is: a one-time enable/disable toggle, a hardware diagnostic that reads its own configuration, a dashboard launcher. Even then, give it an unmistakable name and group (for example, group FtcExampleLib, name prefixed with the library name), so it is obvious in the OpMode list that it came from a library and not from TeamCode. And document it in the README: “this OpMode ships in the library; here is what it does; here is how to tell it apart from your own OpModes.”

Never ship an OpMode that moves a mechanism by default. A shipped tuner that oscillates a motor, a shipped demo that drives, or a shipped test that spins a flywheel will run on a robot whose mechanism cannot safely do that, because the team never configured it — they only added a dependency. Tuners and demos belong in templates, where the team must edit hardware names and limits before they can run. Convenience is not worth a mechanism hitting a hard stop at full power.

Java/Kotlin interop for library authors

A library with both languages has a boundary, and the boundary has rules. Most of them are about nullability and defaults — the two places where Kotlin is stricter than Java and Java callers will not know it until runtime.

Nullability: annotate Java, trust Kotlin types

Kotlin distinguishes nullable (String?) from non-null (String) types at compile time. Java has no such distinction in the language, so Kotlin reads Java types as “platform types” — usable as either, with no compile-time check. For a library, that means:

  • Write Kotlin APIs with explicit nullability. A Kotlin parameter of type DcMotor (non-null) tells Kotlin callers they must pass a motor, and tells Java callers, via generated annotations, that passing null is a contract violation. A Kotlin parameter of type DcMotor? tells everyone that null is expected and handled. Do not leave nullability ambiguous in a public API; ambiguity is a NullPointerException waiting for a Java caller.
  • Defend the boundary in Java code anyway. The Java wrapper in this guide checks motor == null and throws IllegalArgumentException, even though a Kotlin caller could never pass null through the Kotlin type system. Java callers can, and will, through reflection, through older bytecode, or through a careless cast. A null check at a public constructor costs one line and turns a mysterious NullPointerException three calls later into an immediate, named failure at the boundary where the bad value entered.
  • Annotate public Java APIs for Kotlin callers. If your Java code is the public API and Kotlin callers will use it, annotate parameters and return types with @NonNull / @Nullable (from androidx.annotation or JetBrains annotations, as compileOnly or api as appropriate for your setup). Without annotations, Kotlin sees every Java type as a platform type and loses the safety it was designed to provide. With annotations, Kotlin enforces your intent. The FTC SDK itself annotates its APIs this way; follow its lead.

Checked exceptions, SAMs, and other small traps

  • Kotlin has no checked exceptions. A Java method that declares throws IOException can be called from Kotlin without a try/catch, and the exception will still be thrown at runtime. If your Java API declares a checked exception, document it as if Kotlin callers will never see the declaration — because they will not.
  • Single-method interfaces convert to lambdas in Kotlin. A Java interface with one abstract method (a SAM) can be implemented in Kotlin with a lambda. That is convenient for callbacks. It also means changing a SAM interface by adding a second method is a breaking change for Kotlin callers in a way that is invisible in Java. Do not add methods to a SAM interface after publication; add a new interface.
  • Kotlin object singletons are not Java singletons. A Kotlin object is a class with a single INSTANCE field. Java callers access it as MyObject.INSTANCE. If Java callers need a singleton, give them a Java class with a static accessor, or annotate the object's members with @JvmStatic. And reconsider whether the library needs a singleton at all — the limiter chapter argues it usually does not.

Design an API for Java and Kotlin callers

A good FTC library API feels like it was written for the language the caller is using, even though it was written once. That feeling comes from a small number of naming and shape decisions, made before publication, when they are still cheap.

Name things the way the FTC SDK names things

Callers already know the FTC SDK's vocabulary: setPower, getVelocity, setTargetPosition, RUN_WITHOUT_ENCODER. A library that invents synonyms for those concepts (applyDrive, fetchSpeed) forces every caller to learn a second vocabulary for no benefit. Use the SDK's verbs for SDK concepts, and plain English verbs for your own concepts: setTargetPower, update, stop, reset. The example follows this rule throughout. If you cannot name a method with an SDK verb or a plain verb, the method is probably doing two things; split it and the names will appear.

Constructors: few, clear, and delegating

Offer at most two public constructors for a type: one that takes a config object, and one that takes the handful of numbers a caller most often wants. Both should delegate to one private initialization path, so validation and defaults live in one place. The limiter does this. The motor controllers do this. A type with five public constructors, each subtly different, is a type whose callers will pick the wrong one and blame the library when it behaves differently from the one they meant.

For Kotlin types, prefer a primary constructor with default arguments, plus @JvmOverloads if Java callers will construct it directly. For Java types, prefer explicit overloads over a builder for simple configuration, and a builder or config object once the parameter count passes four or five. Do not offer both a builder and five constructors for the same type; pick one idiom per type and be consistent across the library.

Units, ranges, and time: say them in the name or the docs, every time

Every numeric parameter in a public API must answer three questions in its name or its documentation: what unit, what range, and what happens outside the range. The limiter's calculate(double target, double dtSeconds) answers all three: target is in output units (documented as motor power, −1 to 1, clamped), dtSeconds is in seconds (documented as non-negative, rejected if negative). A parameter named rate with no unit is a bug report waiting to happen: rate of what, per what? Name it maxChangePerSecond and the question answers itself.

Prefer doubles for FTC control values, ints for counts. Motor power, velocity, and position targets that come from encoders are often integers in the SDK (getCurrentPosition() returns int), while powers and rates are doubles. Do not convert encoder counts to doubles “for consistency” in a public API that wraps encoder hardware; callers will wonder whether fractional counts are meaningful. Keep the SDK's types at the hardware boundary and convert to doubles only where the math genuinely needs them, inside core.

Stability: what you promise when you tag

Once a version is tagged and published, its public API is a promise. Adding a method is safe. Adding a parameter to an existing method is not — it breaks every caller. Renaming a class, moving a package, changing a return type, or removing a constructor are all breaking changes, even if the new API is better. The versioning chapter explains how SemVer communicates breaking changes. The design lesson is earlier: before the first tag, review every public class, method, and constructor as if you will never be allowed to change it, because after the tag, you effectively will not be — not without a major version bump and a migration note that every consumer must read. Keep the public surface small in v0.1.0. You can always add to it. You cannot easily take away from it.

Documentation on the API itself

Every public class and public method needs a doc comment that says what it does, what its parameters mean (with units), what it returns, and what it throws. That is not bureaucracy; it is the API reference. Most consumers will read your code through IDE hover, which shows the doc comment and nothing else. A public method with no doc comment is a public method whose contract is “guess.” Write the comment when you write the method, while you still remember why you wrote it that way. The example classes in this guide model the level of detail to aim for: one paragraph of purpose, one sentence per non-obvious parameter, and a note for every surprising behavior (such as “call once per loop” or “writes zero immediately”).

Publish to mavenLocal and prove it resolves

Before JitPack ever sees your code, prove that Gradle can publish it and that another project can consume the published form. That proof runs entirely on your computer, in minutes, and it catches the publishing mistakes that are hardest to debug through a web build log.

What mavenLocal is

mavenLocal() is a Maven repository on your own machine, normally under ~/.m2/repository/. The publishToMavenLocal task (provided by the maven-publish plugin you already applied) builds each module's publication and installs the JAR/AAR, the POM (or Gradle module metadata), and the sources jar into that local repository, under the group/artifact/version from the build files. A second Gradle project that declares mavenLocal() as a repository can then resolve your library exactly as if it had come from a remote repository — same coordinates, same metadata, same transitive dependencies — except nothing has left your machine.

Run it

  1. Publish. In the Gradle tool window, expand Tasks → publishing and double-click publishToMavenLocal.
  2. Inspect. Open the Terminal tab and run the find command below. Both modules must appear, each with an artifact, a POM, module metadata, and a sources jar.
BASH
./gradlew publishToMavenLocal
find ~/.m2/repository/com/github/yourname -type f | sort

The find output should show, for each module, the artifact itself (.jar / .aar), the POM (.pom), the Gradle module metadata (.module), the sources jar (-sources.jar), and checksums. If the sources jar is missing, withSourcesJar() is not applied where you think it is. If the POM is missing or names the wrong group/artifact/version, the publication block is wrong. If only one module appears, the other module's publication did not run — check that maven-publish is applied in that module and that its publication is registered, not just declared in a comment.

mavenLocal is a cache, not a clean room. Old publications linger in ~/.m2 under old versions and old group names. If a consumer test “works” but you are not sure which version it resolved, delete the group folder ~/.m2/repository/com/github/yourname/FtcExampleLib/ and re-run both the publish and the consumer build. A test that passes because of a stale artifact from last week is worse than a test that fails honestly today.

Inspect the POM before you trust it

Open the published .pom file for example-ftc and read its <dependencies>. You should see the core dependency with compile scope (because ftc declares it as api). The FTC SDK artifacts, if they appear at all, must appear with provided scope: compileOnly maps to provided in the POM, meaning “needed to compile, provided by the host app at runtime.” If an FTC SDK artifact appears with compile or runtime scope, the compileOnly declaration is not what you think it is, and consumers will get duplicate SDK classes. Fix it now, in the build file, before JitPack builds the same POM for everyone.

Also check the Kotlin stdlib entry. If your public API uses Kotlin types, the stdlib should appear as a dependency consumers will resolve transitively. If it does not appear, Java consumers may compile fine and Kotlin consumers may fail, or vice versa, depending on what else is on their classpath. The api(kotlin("stdlib")) declaration in both modules exists to make this entry appear. Verify it, rather than assuming it.

When mavenLocal passes, you are ready for a consumer test

@TeleOp(name = "Example: Slew Motor", group = "FtcExampleLib")

How JitPack works

JitPack turns a GitHub repository into a Maven repository, on demand, with no account, no server to run, and no signing ceremony. Understanding that sentence — especially “on demand” — explains almost every JitPack behavior that surprises first-time publishers.

The build-on-demand model

When a consumer first requests a version of your library, JitPack clones your repository at that tag (or commit, or branch), runs your Gradle build with publishToMavenLocal on its own machines, and serves the resulting artifacts from jitpack.io as if they were in a normal Maven repository. The first request for a new version is therefore slow: it waits for a full remote build. Later requests are fast, because JitPack caches the built artifacts. If you have ever wondered why the first Gradle sync after adding a JitPack dependency takes minutes and the second takes seconds, that is why. It is not a network problem. It is a build happening somewhere else, for the first time.

Three consequences follow, and all three should shape how you publish:

  • Your repository must build cleanly from a fresh clone, with no local state. No local.properties, no SDK path in a build file, no file that exists only on your machine, no dependency that resolves only from your ~/.m2. JitPack's machines have the Android SDK and a JDK, and nothing of yours. The local mavenLocal test in this guide proves the publication works; a fresh-clone build proves it works without you.
  • The tag is the release. JitPack does not have a separate “publish” step, a staging area, or a web form where you upload artifacts. Pushing a tag is publishing, in the sense that the tag becomes requestable. That is why the tagging chapter insists on verifying locally first: there is no “unpublish this tag, it was a draft” button that erases it from every cache that already fetched it.
  • Build failures are public and logged. Anyone can request a build log for a version on jitpack.io. Treat the JitPack log as a public build log, because it is one. Do not put secrets, tokens, or private URLs in build files or in code that runs during the build. The build files in this guide contain no secrets for exactly that reason.

What JitPack needs from your repo

  • A public GitHub repository (private repositories need authentication setup, which is out of scope for a first free publish — see the troubleshooting chapter for the one-line summary).
  • A Gradle wrapper, committed, so JitPack uses your Gradle version.
  • The maven-publish plugin in each module you want published, with a publication for that module. Without it, JitPack has nothing to publish, and the build log will say so in terms that sound like a Gradle error and are actually a missing-plugin error.
  • A jitpack.yml pinning JDK 17, because JitPack's default JDK is older and AGP 8+ will not build on it.
  • A tag. JitPack builds tags, branches, and commits, but releases are tags. The branches-and-pre-releases chapter explains the pre-release forms and why you should not ship them to a team.

What JitPack does not do

JitPack does not review your code, does not sign your artifacts, has no separate test gate of its own — it runs the default build, which includes tests, so a failing test fails the JitPack build just as it fails a local build, does not host your documentation, and does not notify consumers of new versions. It is a build-and-serve service, not a package manager with curation. Your README, your changelog, and your tag discipline are the curation. JitPack will faithfully build and serve a badly named, undocumented, breaking release if you tag one. The maintaining chapters exist to prevent that.

Cost. JitPack is free for public repositories, with no account needed to consume public builds. That is the reason this guide recommends it first, as requested: a student team can publish and consume a library with no budget, no approval process, and no infrastructure to maintain. If JitPack is ever unavailable, consumers' builds that already have the artifact cached will still work; only first-time fetches of a version are affected. That availability tradeoff is real, and it is the main reason large libraries eventually move to Maven Central. For a first library, it is the right tradeoff.

What is already done

Both modules already apply maven-publish and declare a release publication with the correct group, artifact, and version, following FtcAutoTune's pattern exactly. If you followed the earlier chapters, there is nothing to change in those files for JitPack. Do not add a publishing { repositories { ... } } block pointing at JitPack, Maven Central, or anywhere else. JitPack does not publish by uploading to a repository you configure; it runs publishToMavenLocal on its machines and serves the result itself. A repositories block in your publishing configuration would be ignored at best and would fail the build at worst if it required credentials you did not provide.

jitpack.yml: pin JDK 17

Create jitpack.yml at the repository root with exactly these contents. AGP 8+ requires JDK 17, and JitPack's default JDK is older. Without this file, JitPack will try to build with the wrong JDK and fail with an error that mentions Gradle or AGP compatibility, not the JDK — which is why this two-line file is easy to forget and hard to diagnose without.

YAML
jdk:
  - openjdk17

That is the whole file for this project. JitPack supports additional keys (before_install, install) to override the build commands, but you do not need them: the default Gradle build (./gradlew build publishToMavenLocal) is exactly what you want, and overriding it adds a second place where the build can diverge from your local build. Only override the install command when you have a specific, documented reason — for example, to skip a test that cannot run on JitPack's machines — and document that reason in a comment in the file and in the README. A silent override that skips tests is how untested code gets published with a green build log.

Tag a release

A release is a tag, a changelog entry, and a README that agrees with both. The tag takes ten seconds. The agreement takes discipline, and it is what separates a library people can depend on from a repository people are afraid to update.

Semantic Versioning, in the form FTC teams actually need

This guide uses Semantic Versioning: MAJOR.MINOR.PATCH. For a library, the meanings are about the public API, not about how much code changed:

PartBump whenExample
MAJORYou break the public API: rename, remove, or change the meaning of a public class, method, or parameter.1.0.0 → 2.0.0
MINORYou add functionality in a backwards-compatible way: a new class, a new method, a new overload.0.1.0 → 0.2.0
PATCHYou fix a bug in a backwards-compatible way, with no API change.0.1.0 → 0.1.1

Two corollaries matter for a first library. First, versions starting with 0. are, by SemVer convention, “anything may change at any time.” That is honest for a first release, and it is why the example starts at 0.1.0, not 1.0.0. Do not call a first, untested-in-the-wild library 1.0.0 because the number looks more serious. 1.0.0 is a promise of stability. Earn it with a few real consumers first. Second, once you are at 1.0.0 or beyond, a breaking change must bump the major version, even if the change is small. A one-line rename that breaks every consumer is a major change, no matter how small the diff is.

The v prefix, and the three-way agreement

JitPack uses the tag string exactly as the version. If your tag is v0.1.0, consumers write v0.1.0. If your tag is 0.1.0, consumers write 0.1.0. Both forms exist in the wild — FtcAutoTune's history contains both, which is a cautionary tale, not a pattern to copy. Pick one form and use it for every tag, forever. This guide picks the v prefix, because it is the more common convention for GitHub releases and because it makes tags visually distinct from version numbers in prose.

That choice creates a three-way agreement you must maintain on every release:

  • Git tag: v0.1.0 (with the v).
  • VERSION_NAME in gradle.properties: 0.1.0 (without the v), committed before the tag is created, so the tagged commit contains the matching version.
  • README examples: the JitPack coordinate with the tag string, v0.1.0, updated in the same commit as the version bump.

As checked on 1 November 2026, FtcAutoTune's README still shows v1.0.0 examples while the current tag is v1.4.3. That drift is understandable — the README was written once and the library kept moving — and it is exactly the kind of drift that makes a new consumer copy a stale coordinate, get “artifact not found,” and conclude the library is broken. Update the README in the same commit as the version bump, every time, and check it as part of the pre-tag checklist.

Create the tag and the GitHub release

  1. Commit. Click Git → Commit. Tick all files, type “Release 0.1.0”, and click Commit.
  2. Tag. Click Git → New Tag (Git → Tag → New Tag in some versions). Type v0.1.0, add the message “Release v0.1.0: initial slew-rate limiter library”, and click Create Tag.
  3. Push. Click Git → Push. Set Push tags so the tag goes up too, then click Push.
  4. Release. On GitHub, click Releases → Draft a new release, choose tag v0.1.0, paste the changelog entry as the notes, and click Publish release.

Do not leave the release notes blank, and do not paste the raw commit list. Commit lists are for archaeology.

Tell TeamCode about JitPack

A consumer needs exactly two things: the JitPack repository, and the dependency coordinate. Both go in the Quickstart's Gradle files, which are written in Groovy. This chapter shows where, and warns about the one Quickstart setting that will silently ignore a repository added in the wrong file.

Add the JitPack repository

Gradle resolves dependencies only from repositories it knows about. JitPack is not in the default list, so the consumer must add it. Where to add it depends on how the Quickstart centralizes repositories. Check first, add second:

  • If the Quickstart uses dependencyResolutionManagement in settings.gradle / settings.gradle.kts with repositoriesMode = FAIL_ON_PROJECT_REPOS (as the Pedro Pathing Quickstart does), repositories declared in a module build file are ignored, and adding JitPack there will do nothing. Add it in the settings file's repositories block, alongside mavenCentral() and google().
  • If the Quickstart declares repositories in build.dependencies.gradle (as older Quickstarts do), add it there, in the repositories block at the top of that file.

In Groovy, the line is the same in either file:

GROOVY
repositories {
    mavenCentral()
    google()
    maven { url = 'https://jitpack.io' }
}

If you add the repository in the wrong place, the symptom is “could not resolve” for the JitPack coordinate, with no mention of JitPack in the error. Before concluding the artifact does not exist, check where repositories are declared in that specific Quickstart and confirm the JitPack line is in a block Gradle actually reads. The troubleshooting chapter lists this as the first JitPack consumer failure to check, because it is the most common and the least obvious.

Add the dependency

In the Quickstart's dependency declarations (usually build.dependencies.gradle, applied to TeamCode, or directly in TeamCode/build.gradle), add:

GROOVY
dependencies {
    implementation 'com.github.yourname.FtcExampleLib:example-ftc:v0.1.0'
}

One line is enough for the FTC module, because example-ftc declares api(project(":core")), so example-core arrives transitively. A consumer who wants only the pure logic — for a desktop tool, a test harness, or a unit test in another project — declares example-core alone:

GROOVY
dependencies {
    implementation 'com.github.yourname.FtcExampleLib:example-core:v0.1.0'
}

If a consumer's Quickstart has been converted to Kotlin DSL (rare, but it happens), the same coordinate in Kotlin DSL is implementation("com.github.yourname.FtcExampleLib:example-ftc:v0.1.0"). The coordinate string does not change. Only the surrounding syntax does, as the Gradle chapter explained. Do not publish two different coordinate strings for two DSLs; publish one coordinate and show both syntaxes in the README if you need to.

What the consumer should see on sync

On the first sync after adding the dependency, Gradle will contact JitPack, JitPack will build the tag if it has not built it before, and the sync will take noticeably longer than usual — minutes, not seconds, on a first build. That is expected. The second sync will be fast. If the first sync fails, do not immediately change the dependency line. Read the error: if it names JitPack and a build failure, the problem is in the library's build, and the JitPack log (next chapter) is where to look. If it says the artifact was not found, the problem is the coordinate, the repository location, or the tag — check those three, in that order, before touching the library.

Remove mavenLocal() when you switch to JitPack testing. The local test used mavenLocal() and version 0.1.0. The JitPack test must use the JitPack repository and version v0.1.0, with mavenLocal() removed or moved after JitPack, so you are actually testing the remote artifact and not accidentally resolving the local one again. Forgetting to remove mavenLocal() is how a “JitPack test” passes while JitPack is actually broken.

Trigger the first build and read the log

Do not wait for a consumer to discover that your first tag does not build. Trigger the build yourself, read the log, and fix it before you announce the release.

Trigger the build

  1. Go to jitpack.io and enter your repository URL (https://github.com/yourname/FtcExampleLib) in the lookup box. You do not need an account to look up a public repository.
  2. Find the tag v0.1.0 in the versions list and click Get it (or the equivalent build button for that version). JitPack will queue a build.
  3. Wait. The first build downloads Gradle, the Android SDK components it needs, and all dependencies, then compiles both modules and publishes locally on JitPack's machines. Expect minutes. Do not queue the same build twice because the page looks idle; a second request for the same version joins the same build.
  4. When the build finishes, the page shows a status per artifact (example-core and example-ftc). Both must succeed. A green status for one module and red for the other is a partial failure: the successful module is usable, the failed one is not, and consumers depending on the failed one will fail. Fix the failed module and tag a patch release; do not tell consumers to “just use the core for now” as if that were the release you intended.

Read the build log in order

Click through to the build log. Read it from the top, not the bottom. JitPack logs, like Gradle logs, put the cause early and the consequences late. The useful sections, in order, are:

  • Environment. JDK version, Gradle version, Android SDK. Confirm the JDK is 17 (from jitpack.yml) and Gradle is 8.9 (from the wrapper). If either is wrong, the fix is in jitpack.yml or the wrapper, not in your code.
  • Clone and checkout. Confirm JitPack checked out the tag you meant, at the commit you meant. If the log shows a different tag or a different commit, you pushed the tag from the wrong branch or before the version-bump commit.
  • First failure. The first FAILED task, the first “could not resolve,” or the first compilation error. Fix that one. Everything after it is usually consequence, and fixing consequences first wastes time.
  • Publication. Near the end, the log should show both modules publishing to the local Maven repository on JitPack's machine. If a module builds but does not publish, its maven-publish setup is missing or misnamed, and the artifact will show as “not found” for consumers even though the log looks green. Check the publication list explicitly.

Verify from a clean consumer, not from the log alone

A green JitPack log proves JitPack could build the tag. It does not prove a Quickstart can consume it. After the log is green, go back to the throwaway Quickstart, remove mavenLocal(), set the dependency to the v0.1.0 JitPack coordinate, sync, build, and deploy. Only when that succeeds — on a machine whose Gradle cache has never seen the local artifact, or after clearing the relevant cache entries — is the release verified. The on-robot chapter covers the robot half of that verification. Do not announce the release until both halves are done.

Branches, commits, and pre-releases

Sometimes you need a team to test a change before it is a release. JitPack can build branches and individual commits, and those forms have a place — as pre-release testing, never as the version a team pins for competition.

The pre-release forms

FormCoordinate versionWhat it buildsUse for
Commit hashShort or full SHAThat exact commit.Reproducing a specific build, bisecting a regression.
Branch snapshotmain-SNAPSHOTThe tip of the named branch, rebuilt on request.Testing the latest unreleased work on a test robot.
Tag (release)v0.1.0That exact tag, immutably.Everything a team depends on. The only form to document as “the version.”

The branch-snapshot form is the one that causes trouble. Because it rebuilds from the branch tip, two builds of main-SNAPSHOT on different days can contain different code, and Gradle's caching may serve the older build to a consumer who expected the newer one. That is acceptable for a test robot on a Tuesday. It is unacceptable for a competition robot, where “which code is on the robot” must be answerable exactly. Never document a snapshot as the install instruction, never pin a snapshot in a team's competition code, and never be surprised when a snapshot behaves differently on two machines.

A sane pre-release workflow

  1. Make the change on a branch. Verify it locally with mavenLocal() and the throwaway Quickstart, as in the consuming-locally chapters.
  2. Push the branch. Ask the tester to depend on branch-SNAPSHOT in the throwaway Quickstart only, and to report back with the commit hash they tested (from the JitPack log or the Gradle cache), not just “the snapshot.”
  3. When the change is approved, merge it, bump the version, tag it, trigger the JitPack build, and verify the tagged coordinate in the throwaway Quickstart. Then, and only then, tell consumers the new version exists.

If a tester reports a bug against a snapshot, the first question is always: “Which commit?” A snapshot version string does not answer that question. A commit hash does. Keep the habit of recording hashes in test reports, even for informal testing, and pre-release debugging becomes dramatically easier.

Do not tag pre-releases as if they were releases. A tag named v0.2.0-alpha.1 is a real tag, and JitPack will build it, but consumers who see it in a versions list may assume it is the latest stable release. If you need alpha/beta tags, name them clearly, document them as pre-releases in the release notes, and do not point the README's install instructions at them. The README should always point at the latest stable tag.

JitPack troubleshooting

JitPack failures fall into three buckets: the build failed, the artifact was not found, or the build succeeded but the consumer got stale code. Check the buckets in that order. Do not change the library to fix a consumer-configuration problem, and do not change the consumer to fix a library-build problem.

Bucket 2: artifact not found by the consumer

Work through this list in order, and stop at the first item that is wrong. Do not skip ahead to “the artifact must not exist” until you have checked the first four.

  1. Repository location. Is the JitPack repository line in a repositories block Gradle actually reads for this Quickstart? (See the consumer chapter on FAIL_ON_PROJECT_REPOS.)
  2. Coordinate spelling. Group, artifact, and version, character by character, including capitalization of the GitHub username and repository name, and the v prefix on the version. Copy it from the JitPack page for that tag, not from memory.
  3. Tag exists and is pushed. The tag must exist on GitHub, on the default branch's history (or the branch you tagged from), and be pushed. A local-only tag is invisible to JitPack.
  4. JitPack built it. Look the version up on jitpack.io and confirm a successful build for both artifacts. An artifact that was never built cannot be resolved, and the consumer error will not say “not built yet.”
  5. Stale cache. Only now, clear the relevant Gradle/JitPack cache entries and re-sync. Clearing caches before checking the first four items wastes time and hides the real error.

Bucket 3: stale or wrong code at the consumer

If the consumer resolves the dependency but gets old behavior, check, in order: the version string in the consumer (is it the new tag, or the old one still pinned somewhere?); mavenLocal() still present and shadowing JitPack (remove it for JitPack testing); a snapshot version that rebuilt underneath the consumer (pin a tag instead); and the library's own version — did the tagged commit actually contain the change, or was the change committed after the tag? That last one is more common than it sounds: tagging, then committing “one more fix,” then wondering why the tag does not contain it. The fix is a new tag. Tags do not move.

Private repositories, in one paragraph

JitPack can build private repositories, but consumers need authentication configured to fetch them, which every team must set up individually. For a first, free, public library, that complexity is not worth it. Keep the library repository public, keep the code and the build log public, and keep private team code in the team's private robot repo, consuming the public library. If you later need a private library, that is a separate setup with its own authentication story, and it should not be bolted onto a public library's README as an afterthought.

Run the example on the robot

A library is not verified until it has run on a robot. Unit tests verify logic. A local build verifies packaging. Only a robot run verifies that the FTC wrapper, the hardware map, the OpMode loop, and the limiter behave together, at loop rate, with a real motor.

Before you press start: safety checks

  • The test motor is free to spin: no load that can jam, no hard stop it will hit, no cable it can wind up.
  • The hardware configuration name in the OpMode matches the configuration on the Control Hub exactly (exampleMotor in the template, or your edited name).
  • The rate in the template is low (2.0 per second in the example) and the target power is modest (0.5 in the template). Do not raise either for a first run.
  • The motor does not move until the driver holds gamepad1 A. Verify this by initializing the OpMode and watching the motor stay still before start, and stay still after start with A released.
  • Someone is standing where they can press stop, and the robot is on blocks or the motor is otherwise unable to move the robot unexpectedly. A free-spinning test motor on a robot sitting on the floor can still move the robot if it is a drive motor. Do not test a drive motor with this template while the robot is on the floor.

Run it and watch the telemetry

  1. Deploy. In Android Studio, choose the TeamCode run configuration, click Run (the green play button), and pick the Control Hub in the device chooser.
  2. Select the OpMode. On the Driver Station, select Example: Slew Motor in the FtcExampleLib group.

Initialize, then press start. With A released, telemetry should show target 0.00 and applied 0.000, and the motor should be still. Hold A: the target shows 0.50, and the applied power should climb smoothly — roughly 0.1 per 0.05-second loop at a rate of 2.0 per second, reaching 0.5 in about a quarter of a second — rather than stepping to 0.5 immediately. Release A: applied should fall smoothly back toward zero. Press stop: the motor must stop immediately, not ramp down over the limiter's time constant, because stop() writes zero directly.

If the motor steps instantly to full power, the limiter is not in the path: check that the OpMode calls controller.update(dt) and not motor.setPower() directly, and that dt is the elapsed time since the previous loop (the template resets its timer each iteration). If the motor does not move at all, check the hardware name, the direction, and whether another OpMode or configuration is holding the motor. If the motor oscillates or stutters, the loop period is probably irregular or dt is wrong — log dt to telemetry for a few loops before changing the limiter.

What a successful run proves — and what it does not

A successful run proves: the AAR merged into the app, the OpMode was discovered, the hardware map lookup worked, the wrapper configured the motor, the limiter ran at loop rate, and stop() behaved. It does not prove the limiter is correctly tuned for your mechanism, that the rate is right for a loaded flywheel versus an unloaded test motor, or that the wrapper is safe for a mechanism with gravity or hard stops. Those are per-mechanism judgments, made by the team that owns the mechanism, with the mechanism in front of them. The library gives them a correct, testable tool. It does not make the judgment for them. Say so in the README, in plain language, so no team mistakes “the example ran” for “this rate is safe for my arm.”

Iterate and release v0.2.0

Releasing the second version is where most libraries either become maintainable or become a pile of tags. The procedure is the same as the first release, with one addition: you must decide, explicitly, whether the change breaks the public API, and version it accordingly.

A worked iteration: add a velocity helper, without breaking anything

Suppose a consumer asks for a helper that converts a target velocity to a power using the limiter, for a flywheel that is driven open-loop. You add a new method to ExampleMotorController — say, setTargetVelocity(double ticksPerSecond, double ticksPerSecondAtFullPower) — that stores a velocity target and converts it to a power target inside update(). You add no parameters to existing methods, rename nothing, and remove nothing. That is a backwards-compatible addition: a MINOR bump, 0.1.0 → 0.2.0.

Now suppose instead you realize the limiter's calculate method should take milliseconds instead of seconds, and you change the parameter. That breaks every caller, including the template OpMode and every team that already adopted v0.1.0. That is a MAJOR change, even though it is one parameter. In a 0.x library, SemVer allows breaking changes in a MINOR bump, but the honest practice is the same: say so loudly in the changelog, bump the minor version, and do not pretend the change was compatible. Better still: do not change the unit. Add a new method with the new unit in its name (calculateMillis is ugly; a better design is to keep seconds, the SI unit, and document it) and deprecate the old one. Breaking changes should be rare, deliberate, and announced — not slipped into a patch release because the diff was small.

The iteration procedure

  1. Make the change on a branch. Add or update tests in core for any logic change. Update doc comments for any API change.
  2. Verify locally: ./gradlew clean build, publishToMavenLocal, throwaway Quickstart sync and build, on-robot run if the change touches hardware behavior.
  3. Write the changelog entry before tagging: Added / Changed / Fixed / Breaking, in plain language, with the version number.
  4. Bump VERSION_NAME, update the README coordinate, commit, tag (v0.2.0), push, create the GitHub Release with the changelog entry as the notes.
  5. Trigger the JitPack build for the new tag, read the log, verify in the throwaway Quickstart with the new coordinate. Announce only after verification.

Deprecation, done kindly

When you replace an API, do not delete the old one immediately. Mark it @Deprecated with a message naming the replacement, keep it working for at least one minor release, and remove it only in a major (or, for 0.x, clearly announced minor) release. Java's @Deprecated and Kotlin's @Deprecated("...", ReplaceWith("...")) both exist for this purpose; use the one for the language the deprecated API is written in, and make the message actionable: “Use setTargetPower instead. This method will be removed in 0.3.0.” A deprecated method with no replacement named is a dead end, not a migration path.

Versioning, changelogs, and docs

A library's documentation is part of the library. A team deciding whether to depend on you will read the README before they read the code, and they will decide based on whether the README answers three questions in under a minute: what does it do, how do I add it, and what do I copy to use it.

The README a team needs

Write the README before the first tag, and keep it in the same repository as the code. It should contain, in this order:

  1. One paragraph: what the library does, in plain language, with the mechanism or problem it solves named explicitly.
  2. Install: the JitPack repository line and the dependency line(s), for the current stable tag, in Groovy (the Quickstart's language), with the FAIL_ON_PROJECT_REPOS note if it applies to your consumers' Quickstart.
  3. Use: the smallest complete example — the template OpMode, or a code snippet showing construction, update() in the loop, and stop() — that a team can copy and run.
  4. Versions: which FTC SDK / Quickstart versions the current release was tested against, and the compileSdk / minSdk the library uses, so a team can check compatibility before adding the dependency.
  5. Changelog link: a link to the releases page, or a CHANGELOG.md in the repo, with the latest version's changes summarized.
  6. License and contributing: the license name (next chapter) and how to report a bug or propose a change.

Do not put the entire API reference in the README. The API reference lives in doc comments and, if you generate it, in hosted docs. The README is the front door, not the whole house. A README that tries to document every method will go stale the moment a method changes, and stale documentation is worse than a link to the source, because it is confidently wrong.

License and attribution

A repository with no license is not “free to use.” Under default copyright law, it is “all rights reserved,” and other teams cannot legally copy, modify, or distribute it — including by depending on it in a robot that competes. A license file is not paperwork. It is the permission slip that makes sharing legal.

Pick a license before the first tag

For FTC libraries, the common choices are permissive licenses that let teams use, modify, and distribute the code, including in competition robots, with attribution:

Any of the three is a defensible choice for a first FTC library. Pick one, put the full license text in a LICENSE file at the repo root, name it in the README, and do not change it after the first tag without understanding that existing consumers relied on the old license. Do not write your own license. Do not copy a license text and edit its terms. And do not leave the license choice to “later” — “later” is after teams have already depended on unlicensed code, which helps no one.

This is not legal advice. If your library will be used commercially, if it incorporates code under a copyleft license (such as GPL), or if your school or team has rules about open-source contributions, ask a teacher, mentor, or other appropriate adult before choosing. The guidance here is the common practice for permissive FTC libraries, not a substitute for advice about your specific situation.

Attribution and third-party code

If your library includes code adapted from another project — a controller ported from FTCLib, geometry adapted from Pedro Pathing, a dashboard pattern learned from FtcAutoTune — keep the original license notice with the adapted code, credit the source in the README, and comply with that project's license terms. “I rewrote it in my own words” does not erase the obligation if the code is a derivative work, and it certainly does not erase the courtesy of credit. When in doubt, credit generously and keep notices intact. The FTC community is small; reputation travels, and generous attribution costs nothing.

The same applies in reverse: if someone adapts your code, your license tells them what they must do. A clear license and clear attribution in your own repo make it easy for others to do the right thing with your work, which is the whole point of publishing it.

Final checklist and what is deliberately not here

Use this chapter as the gate before every tag. If any box is unchecked, the tag waits. Tags are cheap to delay and expensive to fix.

Pre-tag checklist

  • ./gradlew clean build succeeds in a fresh clone, with no local-only files.
  • core tests pass, and the test suite runs in seconds with no flakes.
  • publishToMavenLocal produces both artifacts, both POMs, and both sources jars, with the right group/artifact/version.
  • The throwaway Quickstart syncs, builds, and deploys with the local artifact, and the template OpMode initializes without error.
  • VERSION_NAME, the README coordinate, and the changelog all agree on the version, and the README points at the tag form (vX.Y.Z).
  • jitpack.yml pins JDK 17, and the Gradle wrapper is committed for the Gradle version you tested with.
  • No implementation dependency names org.firstinspires.ftc. All FTC dependencies are compileOnly.
  • No public API was added, renamed, or removed without a doc comment and a changelog entry.
  • The LICENSE file exists, the README names the license, and third-party attributions are intact.
  • The JitPack build for the tag is green for both artifacts, verified in a clean consumer, and the on-robot run behaves as the on-robot chapter describes.

What is deliberately not here, and where to learn it next

  • Maven Central. Skipped by design for this guide, as the welcome chapter explains. When you outgrow JitPack, learn the Sonatype Central Portal flow: namespace verification, GPG signing, complete POM metadata, and sources/Javadoc jars. Pedro Pathing's build files (the deployer plugin configuration) are the working example to read, and the Central Portal documentation is the authority to follow — not a blog post from before the OSSRH shutdown.
  • Dairy Foundation. Not a self-serve host. If your library is built on Dairy Core and you want it in the Foundation, reach out to Dairy, as their documentation invites library authors to do. Do not present Dairy hosting as an option you can enable by editing a build file.
  • Dashboards and web tuners. A bundled web UI (assets + a small HTTP server, as FtcAutoTune and Pedro AutoTune both ship) is a second library feature, not a first one. Build it after the library shape in this guide is proven, and keep the web code out of the core module.
  • OpMode scanning frameworks, command schedulers, and annotation processing. Powerful, and easy to get wrong in ways that break every consumer's OpMode discovery. Learn them by reading Dairy, Pedro's TunerScanner, and the FTC SDK's own scanning code, in that order, before writing your own.
  • Native code. JNI and the NDK have no place in a first FTC library. If you think you need native code for performance, profile the Java/Kotlin implementation first. The FTC control loop runs at tens of hertz; a well-written JVM controller is rarely the bottleneck.

The next step after this guide is not a bigger guide. It is a smaller library, published, used by one other team, and iterated on based on what that team actually needed. Ship the small thing. Listen to the first consumer. Then write the next chapter of the library — not the next chapter of the guide — based on what they asked for.
